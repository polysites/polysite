# Polysite — Technical Architecture

_Written 2026-09-20 and kept current; last revised 2026-10-11 (Known Issues now run to #68)_

## Overview

Polysite is a centralized, static-first multisite CMS platform. This document describes the system as actually built and verified, not just as planned — every component below has been built, run, and tested end to end.

## Repository Structure

Independent git repositories, not one monorepo with everything in it:

- **`polysite`** (core platform) — `github.com/polysites/polysite`. Generic, reusable across clients: the Nuxt app shell, Payload CMS, infrastructure config (Docker Compose, Caddy, GitHub Actions), and composables shared by every client theme.
- **`polysite-themes`**, **`polysite-theme-<name>`** (themes) — the starter theme and developer guide, plus one repo per client theme, nested at `themes/` inside the core repo's working directory but each with its own independent `.git` and commit history (excluded from the core repo via `.gitignore`). A theme carries everything specific to one client: branding, layout, and any client-only pages/components. This split keeps the core reusable while each client's customization lives in its own versioned, independently-deployable package — and per Known Issue #30, *all* of them get extended into the same running app at once, with a per-Site field choosing which one actually renders for a given request.
- **`polysite-plugins`** (plugins) — optional capabilities and content types, nested at `plugins/` the same way (see "Polysite Plugin System" below).

Themes and plugins are both optional: the core builds and runs with neither (Known Issue #56).

Inside the core repo:

```
apps/
  web/    Nuxt — public multisite frontend (generic core)
  cms/    Payload — editorial cockpit
themes/                    optional; each theme is a separate git repo, gitignored from core
plugins/                   optional; the plugins repo, gitignored from core
backup/ deploy/ tests/        the backup tool and policy, deploy.sh, and the smoke / end-to-end / backup / deploy tests
docker-compose.yml         production-parity local stack
docker-compose.dev.yml     fast local dev override (hot reload, schema auto-pushed)
docker-compose.prod.yml    production stack (published images, Cloud SQL, real domains)

.github/workflows/         ci.yml (checks), release.yml (tag to images), deploy.yml (manual deploy), docs.yml (docs site)
docs/                      Guides, Architecture, Brand guide
```

## Infrastructure

The pilot runs on a single Google Cloud Compute Engine VM with Docker Compose and no container orchestrator: Kubernetes, Docker Swarm and Cloud Run were each evaluated and rejected **for the pilot** (see the product requirements' Infrastructure & Deployment section for why). That was a decision for one client's traffic, not a limit of the product: since then Kubernetes is offered as a deployment option (a Helm chart, Known Issue #71) with its limits documented, and the single VM stays the reference path. [Deployment options](/guide/deploy/) compares them. The VM keeps a two-disk layout: a disposable OS disk and a separate data disk holding uploaded media, the Redis AOF file, and container configuration, with scheduled snapshots on the data disk only.

Docker (not Podman — an earlier decision, reversed because Docker was already installed and standardized on both the client's local machine and the server) runs everything via Docker Compose. **No language runtimes live on the host** — all Node.js work happens inside containers; this was an explicit correction made mid-build after Node was briefly installed locally for scaffolding verification.

DNS is managed in Cloudflare. Caddy is the reverse proxy and TLS terminator for every site: it requests and renews a Let's Encrypt certificate automatically per hostname as each one is added to its config, whether that site is a subdomain under one wildcard-friendly domain or an entirely separate root domain — so there's no dependency on wildcard DNS being available anywhere, and no manual certificate management.

## Container Topology

Six services in local dev (`docker-compose.yml`, project name `polysite`, so containers are `polysite-cms-1`, `polysite-web-1`, `polysite-db-1` and so on):

| Service | Role |
|---|---|
| `caddy` | Reverse proxy, TLS, static file serving |
| `web` | Nuxt (public site) |
| `cms` | Payload CMS (admin + API) |
| `db` | PostgreSQL (local dev only) |
| `redis` | Redis, AOF-persisted (not yet wired to app logic — see Not Yet Built) |
| `backup` | Nightly database + media backup, weekly test restore (`backup`, Known Issue #44) |

A seventh, `restore`, sits behind the `restore` profile and runs only on purpose (`docker compose --profile restore run --rm restore latest --yes`).

Production (`docker-compose.prod.yml`) pulls published, versioned images instead of building (see Deployment Pipeline), drops `db` and adds `cloudsql-proxy`, a secure tunnel to the managed Cloud SQL instance — the standard pattern for a non-GKE/non-Cloud-Run VM talking to Cloud SQL without exposing it publicly. In local dev `cms` and `web` also run with `no-new-privileges` and all Linux capabilities dropped; the images run as the unprivileged `node` user (Known Issue #58).

## Request Routing (Caddy)

One Caddy config serves both the public site and the CMS admin, using two virtual hosts driven by env vars:

- **`{$SITE_SCHEME}://{$SITE_DOMAIN}`** (default `http://localhost` in dev): serves static files directly from a shared volume (`file_server` with `pass_thru`, falling through to Nuxt for anything not a real file on disk), proxies `/api/*` to `cms` (so browser-side fetches never need to resolve a Docker-internal hostname), and proxies everything else to `web`.
- **`{$CMS_SCHEME}://{$CMS_DOMAIN}`** (default `http://admin.localhost`): proxies entirely to `cms`.

Two reusable snippets add headers for what the CMS answers (the public site's own pages get theirs from the web app's `nuxt-security`): `api_headers` (`nosniff`, a referrer policy, `Strict-Transport-Security`) on the API and uploaded files, and `admin_headers` (the same plus `X-Frame-Options: DENY` and `frame-ancestors 'none'`) on the admin domain. Request bodies are capped in Caddy as well as in the app: 64 KB for `/api/form-intake/*` (a chunked body declares no length for the app to check), 100 MB for the rest of the API and the admin. Uploaded files are served with `Cache-Control: public, max-age=86400` on the public sites. Sign-in and password-reset throttling is not in Caddy (the stock image has no rate limiting) but in the CMS (`auth/ipThrottle.ts`), which reads the address Caddy puts last in `X-Forwarded-For`, so port 3001 must never be published (Known Issue #67).

The scheme is a separate variable from the domain (`SITE_SCHEME`/`CMS_SCHEME`, default `http`) because Caddy auto-upgrades `localhost` to HTTPS by default even without an explicit scheme — a real 308-redirect-to-untrusted-cert bug hit and fixed during verification. Production sets both scheme vars to `https`, which switches Caddy into its normal automatic-HTTPS mode.

### Loading a page (server-rendered)

```
Browser --GET /--> caddy --> web (SSR)
                                          |
                                 usePayloadPage(slug)
                                          |  (apiBaseInternal, direct)
                                          v
                                    cms --> db
                                          |
                          <-- rendered HTML returned to browser
```

### A client-side API call (after the page has loaded)

```
Browser --fetch("/api/pages?where...")--> caddy
                                            |  /api/* handle block
                                            v
                                      cms --> db
```

### Publishing a change (cache revalidation)

```
Editor clicks Publish in cms admin
        |
        v
Pages.ts afterChange hook fires
        |
        v
POST web:3000/api/revalidate  (x-revalidate-secret header)
        |
        v
useStorage("cache").clear()  inside web
        |
        v
Next request to any page renders fresh; the isr route rule
caches it again from there
```

## Application Layer: Nuxt (`apps/web`)

Server-rendered on every request (no build-time static prerendering — removed after it conflicted with fetching page content from a CMS that isn't reachable during the isolated Docker build step). Caching comes from a Nitro `routeRules` entry (`"/**": { isr: true }`), invalidated on demand by a `/api/revalidate` webhook endpoint that Payload calls on publish. Since Nuxt/Nitro has no Next.js-style ISR as a turnkey default, the webhook's actual mechanism is a full cache clear (`useStorage("cache").clear()`) rather than a surgical per-path purge — documented as an intentional simplification, cheap at this traffic scale.

A small set of composables carries the CMS-fetching logic, shared by every page and every client theme (`apps/web/composables/`):

- **`usePayloadPage(slug)`** — fetches a single Payload `pages` document by slug, for the request's own site.
- **`useSite()`**, **`useSiteBranding(site)`** — the current `Site` record and its colours, fonts, navigation and footer (Known Issues #28, #30).
- **`useSiteLanguage()`**, **`useT()`** — the language of the address and the fixed-word dictionaries (Known Issue #63).
- **`useFormIntake()`**, **`usePageSeoMeta()`** — form behaviour (Known Issue #47) and the page `<head>` (Known Issue #25).

It splits its API base URL by execution context: server-side (SSR) calls go directly to `cms` over the Docker network (`apiBaseInternal`), while client-side calls use a relative `/api` path that Caddy proxies to the CMS (`public.apiBase`). This split exists because `http://localhost:3001` — the original single value — resolves to the `web` container itself during SSR, not the CMS, and port 3001 was never published to the host either way; a real build/runtime failure, not a hypothetical one.

The homepage (`pages/index.vue`) and the catch-all page (`pages/[...slug].vue`) are both in this app, theme-agnostic: the page is drawn by `BlockRenderer`, which picks each block's component from the site's theme (Known Issues #30, #40). The core also has a plain `layouts/default.vue` and `error.vue` (a Polysite-branded 404 and error page that follows the visitor's language) for a site with no theme.

## Application Layer: Payload CMS (`apps/cms`)

Payload 3, which mounts as routes inside a Next.js app rather than running standalone. The `(payload)` route-handler files (`admin/[[...segments]]`, `api/[...slug]`, `api/graphql`, `api/graphql-playground`, `layout.tsx`, `admin/importMap.js`) were pulled directly from the `create-payload-app` npm package's bundled template rather than hand-typed, to avoid guessing boilerplate that Payload itself generates and maintains.

**Collections:**

| Collection | Purpose | Access control |
|---|---|---|
| `users` | Editors/admins. `role` (relationship to `roles`, dynamic, not a hardcoded enum — Known Issue #34) + `isSuperAdmin` (the one hardcoded, non-role bedrock flag) + `assignedSites` (which sites this user can touch — the multi-tenant plugin's array field as of Known Issue #29, not hand-written) | Super-Admin-only create/update/delete; read is also Super-Admin-only, with a self-by-id exception (a user can fetch their own document) — see Known Issue #36, which fixed this from a previous, real gap where `read` was omitted entirely and defaulted to Payload's public `() => true`. `unlock` is Super-Admin-only; sign-in and forgot-password calls are limited per address (`auth/ipThrottle.ts`) and the session cookie is `Secure` over https (Known Issue #67); a plugin keeps per-user state in its own collection, not here |
| `roles` | The dynamic half of RBAC (Known Issue #34): `name`, `modules` (which collections this role can touch), `operations` (create/read/update/delete/publish/unpublish/cloneAcrossSites, applied uniformly across every listed module), `manageSiteSettings`. Ships pre-seeded with 3 (Super Admin, Site Admin, Site User) | Super-Admin-only read/write, with a self-role-by-id exception (a user can resolve their own assigned role) — previously any authenticated user could read every role; see Known Issue #36 |

| `pages` | Static/informational pages: `site` (injected by the multi-tenant plugin), `title`, `slug`, `_status` (native drafts, up to 25 versions, scheduled publish; Known Issue #61), `content` (blocks). | `media` | Uploaded files (images), site-scoped | Public read; capability-gated write |
| `forms`, `form-submissions` | The dynamic form builder (`@payloadcms/plugin-form-builder`), site-scoped. Submissions are filed under their form, read-only for everyone (no create, edit or delete), exportable as CSV, and checked on the server (hidden trap field, signed token, rate limit, ALTCHA or Turnstile). Known Issues #51-#52 | Capability-gated, scoped to assigned sites |
| `redirects` | Managed 301/302 redirects per site, to a page, a file, a form or an external URL | Capability-gated, scoped to assigned sites |
| `site-urls` | The index of every address a site answers to (pages, redirects and any plugin's public content), built by `@payloadcms/plugin-search` as content is saved, so two things can't claim the same one; each live entry also carries its plain text in a hidden, per-language `searchText` (Known Issue #68) | Generated (no manual create). Visitors, and roles with no content permission, read only `published`/`active` entries; roles that can read pages, redirects or a routable content type read all (still per site); update and delete (the Reindex button) need `manageSiteSettings` (Known Issue #67) |
| `privacy-requests` | The per-site register for finding, exporting and erasing one person's information, with a deadline tracker | Capability-gated, scoped to assigned sites |

Site-scoped access control (`pages`, `media`) is `@payloadcms/plugin-multi-tenant` (Known Issue #29) layered on top of the RBAC capability matrix (Known Issue #34), not hand-written `Where` filters — the plugin ANDs a `{ site: { in: <user's assigned sites> } }` constraint onto each collection's own access result automatically, and Super Admins bypass it entirely via `userHasAccessToAllTenants`. This is the concrete implementation of "editors assigned to Site A cannot see or modify assets belonging to Site B" from the product requirements. Commitments cards are no longer their own collection — see Known Issue #26.

Collections that plugins add (posts, the settings and log collections of email, auth, search, share and the rest) are not in this table: each plugin's README lists its own, and the core only wires them in through the extension points described under Polysite Plugin System.

**Database:** PostgreSQL via `@payloadcms/db-postgres`. Payload's Postgres adapter only auto-syncs schema outside of `NODE_ENV=production`; production mode requires checked-in migrations, applied via `npx payload migrate` — wired into the Dockerfile's `CMD` to run before `npm start` on every container start (a no-op if nothing changed). This was a real bug (`relation "pages" does not exist`) caught during first end-to-end verification, not a preemptive guess. The core's migrations hold core tables only (one baseline, `core_baseline`); each plugin ships its own and the adapter runs them after the core's (Known Issue #64).

## Theme Layer (`polysite-theme-starter`, `polysite-theme-<client>`, ...)

A [Nuxt layer](https://nuxt.com/docs/getting-started/layers) — a self-contained package of pages/components/config that another Nuxt app "extends." As of Known Issue #30, `apps/web/nuxt.config.ts` extends **every** theme repo at once, found by scanning `themes/` at start (Known Issue #32; `extends: LAYER_PATHS`, local filesystem paths on purpose, because `github:` layers can't see a private repository). Which theme actually renders for a given request is **runtime data** (`Sites.theme`), not a per-deployment build choice — see Known Issue #30 for the full mechanism (multiple themes, one running app, no new container per theme). The plugins' `web/` layers are found and extended the same way.

Each theme repo holds its own `layouts/<theme-name>.vue` (header/footer chrome) with that client's structure. **All copy and imagery in them are placeholders**, not any client's real content: this was a deliberate line held even after a client asserted authorization to reuse their live site's exact text/logo/photos, since verbatim reproduction of substantial copyrighted text and rehosting real photos/logos isn't something built into the platform regardless of the asserted permission — the client supplies that content directly (via the CMS, or as asset files) rather than it being scraped from their live site.

**Blocks live in themes, not in the core (Known Issue #40).** The core `apps/web` is the engine: data fetching, routing, SEO, and a plain fallback for each block. A theme supplies the designed blocks as `components/<theme>/<Name>Block.vue`, and `BlockRenderer` picks per site: the site's theme first, then its `parent` (set in `theme.json`), then the core fallback. `polysite-theme-starter` is the complete reference theme (all nine blocks, a layout, and a design-tokens stylesheet) meant to be copied; a client theme can declare it as its `parent` and override only what it changes. Its layout places the optional plugins' parts through `<SiteSlot>` (search box, language switcher, share buttons; Known Issue #57). Theme CSS is scoped to a class on the layout root (`.theme-starter`) because all themes share one build.

Because every theme depends on `usePayloadPage`/`useSite`/`useSiteBranding`, all core composables, Nuxt's layer auto-import system resolves them across every layer boundary with no extra wiring — each theme only needs to call them. `useSite()` (Known Issue #28) resolves the current `Site` doc the same way `usePayloadPage` resolves the current `Page` — by the request's own hostname. `useSiteBranding(site)` (Known Issue #30) is the shared, **synchronous** helper every theme's layout calls with that already-resolved `site` ref to compute colors/fonts/nav/footer/social-link data — deliberately not async itself, after a real bug: an earlier version awaited `useSite()` internally before calling `useHead()`, which crashed with "a composable... called outside of a plugin/setup function" the moment two themes existed to actually exercise it, because Vue only restores a component's Nuxt-instance context across an `await` for the setup function's *own* top-level await, not one buried inside a function setup merely calls.

**Styling:** Tailwind CSS v4 as of Known Issue #28, turned on via a one-line `apps/web/assets/css/main.css` (`@import "tailwindcss";`) referenced from `nuxt.config.ts`'s `css` array — no separate `@nuxtjs/tailwindcss` install needed, since `@nuxt/ui` (already a module) pulls in `tailwindcss`/`@tailwindcss/vite` as its own dependency. Used directly as utility classes on plain HTML elements in the homepage's blocks and each theme's `layouts/<theme-name>.vue`; `@nuxt/ui`'s own components aren't used. Per-site brand colors (`Sites.primaryColor`/`secondaryColor`) are wired in as CSS custom properties (`--brand-primary`/`--brand-secondary`, set inline on the layout's root element from `useSite()`) rather than baked into the Tailwind build, since Tailwind's utility classes are generated at build time and can't know a per-request value — every block references them via Tailwind's arbitrary-value syntax (`bg-[var(--brand-primary,#f26522)]`, with a literal fallback for resilience). Icons throughout (including the wireframe's `lucide-vue-next` icon set) render through the already-installed `@nuxt/icon` using `lucide:*` names (e.g. `<Icon name="lucide:menu" />`) — confirmed Iconify's bundled Lucide collection covers every icon needed, so no new icon package was installed.

**Tailwind and the layers.** Tailwind v4 skips nested git repositories, and every theme and plugin web layer is one, so a class used only inside a layer generated no CSS (Known Issue #28). Neither a glob nor one hardcoded name held up, so `nuxt.config.ts` writes `apps/web/assets/css/layer-sources.css` (git-ignored, rewritten at every start) with an `@source` line per theme and plugin layer it found, and `main.css` imports it. A new theme or plugin layer is therefore picked up by restarting the web container, with no edit to the core.

**Per-site typography** works the same way as colors: `Sites.headingFontFamily`/`bodyFontFamily` (plain CSS `font-family` names) drive `--font-heading`/`--font-body` custom properties the same way `primaryColor`/`secondaryColor` drive `--brand-primary`/`--brand-secondary`, and `Sites.googleFontsUrl` (the literal `<link>` href Google Fonts itself generates once you pick families/weights) is injected via `useHead()` reactively off `useSite()` — no font is loaded at all until a Site's record actually sets one. `h1`/`h2`/`h3`/`h4` get `--font-heading` via a small global rule in `main.css`; everything else inherits `--font-body` from `.site-shell`'s own inline `font-family` (custom properties and `font-family` both inherit down the DOM regardless of component boundaries, so this needs no per-block wiring).

**A real client's brand values live only as CMS data, never in git.** Colors and font *choices* are `Sites` field data, set through the admin or API like any other content, and are never hardcoded into this repo's shared theme code, whose own defaults stay the original placeholder values (`#f26522` etc.) for anyone cloning or reusing it. A licensed typeface can't be bundled without a license; a free Google Fonts substitute stands in for it. What stays fictional in the repository regardless, per the placeholder-content rule above: names, logo artwork and all copy. The `Sites.logo`/`favicon` upload fields stay empty in the repo; a real deployment uploads its own logo file there.

**Docker build implication:** `web`'s build context is the repo root, not `./apps/web`, so the build can see `apps/web` and every sibling `themes/polysite-theme-*` directory it extends. The Dockerfile mirrors the exact relative path structure (`/repo/apps/web`, `/repo/themes/...`, `/repo/plugins/...`) with a single `COPY` of the whole `themes/` and `plugins/` folders (Known Issues #32, #56), so the same `extends` paths resolve identically inside the image as on disk, and `docker-compose.dev.yml` bind-mounts the whole folders, so a new theme needs no compose or Dockerfile edit. The published images hold the core only; a site that uses themes or plugins builds its own image from source (see Deployment Pipeline). CI builds both images with empty `themes/` and `plugins/` folders.

## Data Flow: Petition Intake (designed, not yet wired)

Per the product requirements, petition/form submissions are meant to flow: intake endpoint → Redis queue (immediate response to the browser) → worker draining the queue into Postgres at a controlled rate → a Redis counter serving the public live signature count without querying Postgres per page view. Redis is running with AOF persistence (`appendonly yes`, `appendfsync everysec`) in both compose files, but no application code exercises this path yet — petitions/forms are an explicitly later Rollout Plan phase, deferred behind the current static-page Prototype.

```
Browser submit --> intake endpoint (not yet built)
                          |
                          v
                    redis queue --> Redis counter
                          |                  (public live count)
                          v
                  worker (not yet built) --> db
```

## Deployment Pipeline

A release and a deploy are two separate acts (guides: `docs/guide/releasing.md`, `docs/guide/deploying.md`). Pushing a tag deploys nothing.

- **`ci.yml`** — on every push and pull request, and called by the release workflow so a release runs exactly the same gates: lint and unit tests for both apps, the migration check (`npm run check:migrations`), `docker build --target run` of both images with empty `themes/` and `plugins/` folders, the fresh-install smoke test (`tests/smoke/run.sh`, then the workflow, i18n and security end-to-end checks), and a plugin end-to-end job that runs only when the `PLUGINS_DEPLOY_KEY` secret lets it read the plugins repository (otherwise it reports itself skipped and passes).
- **`release.yml`** — on a `v<semver>` tag: checks the tag against `VERSION`, both `package.json` files and `CHANGELOG.md`, runs the CI gates, builds the cms, web and backup images, scans them, pushes them to the registry by version, smoke-tests the pushed digests and drafts a GitHub release. A manual run is a dry run that pushes nothing.
- **`deploy.yml`** — manual only (`workflow_dispatch`, with a version or a rollback box, behind the `production` environment). SSHes into the VM (port 3333, non-default) with a key stored in GitHub Secrets, checks out the tag and runs `deploy/deploy.sh`: backup and test restore, the migrations in a one-off container, one service switched at a time behind health checks, an automatic rollback if one fails. Rollback is "deploy the previous images" (`--rollback`), not a revert of a release.
- **`docs.yml`** — builds this documentation site on every change under `docs/`, so a dead link fails the build; publishing to GitHub Pages is a manual run.
- **Dependabot** (`.github/dependabot.yml`) — weekly npm updates for both apps with the Payload packages in one pull request, monthly for the docs, Docker base images (Node LTS lines only) and the Actions (every action is pinned to a commit SHA with its release in a trailing comment, which Dependabot rewrites; Known Issue #69).

The published images contain the core only. Themes and plugin web layers are Nuxt layers fixed at build time and plugin admin components go through Next's import map, so an install that uses any builds its own image from source and points `POLYSITE_CMS_IMAGE` / `POLYSITE_WEB_IMAGE` at it.

**Deploy key model:** a dedicated SSH keypair scoped to the `polysite` repo only (added as a GitHub Deploy Key with write access, not tied to any personal GitHub account), rather than the assistant holding standing personal SSH/API credentials. Verified with a real push (not just a dry-run, which can pass without proving server-side write permission) before the personal key it initially supplemented was retired.

## Secrets & Configuration

`.env` (gitignored; `.env.example` checked in) for the Prototype phase, loaded via Docker Compose's `env_file`. Deliberately **no shared `NODE_ENV`** in `.env` — both `apps/web` and `apps/cms` set `NODE_ENV=production` themselves in their Dockerfiles, and a shared `NODE_ENV=development` was found to override that via `env_file`, breaking Payload's production-mode behavior. Planned post-Prototype upgrade: Docker Compose's file-based `secrets:` (mounted at `/run/secrets/`, not exposed as an environment variable, no Swarm mode required). Every service currently gets the whole `.env` (the web and Caddy containers included), which is why the secrets that matter are also checked at start.

With `SITE_SCHEME` or `CMS_SCHEME` set to `https`, `payload.config.ts` calls `assertProductionSafe()` (`utils/productionChecks.ts`) and the CMS refuses to boot when `PAYLOAD_SECRET` (and `REVALIDATE_SECRET`, `NUXT_REVALIDATE_SECRET`, `POSTGRES_PASSWORD` where set) is a placeholder or under 32 characters, or `CMS_DOMAIN` is empty (`POLYSITE_ALLOW_WEAK_SECRETS=1` switches it off); the first administrator then also needs `POLYSITE_SETUP_TOKEN` (`setup/policy.ts`, `POLYSITE_ALLOW_OPEN_SETUP=1` lifts it). Every variable is described in `docs/guide/configuration.md`, and the operator's view of these checks is `docs/guide/security.md`.

## Known Issues Found and Fixed During Build

Kept here as a record, since each was a real, reproduced failure rather than a hypothetical. The numbers are stable and sequential (#1 to #68): other docs and code comments refer to "Known Issue #N", so a new entry goes at the end with the next number, and an old one is corrected in place, never renumbered. Entries are history: where a later entry changed the picture, it says so, and the sections above describe the system as it is now.

1. **Root-path routing gap** — the homepage never called the CMS at all; a Payload page with slug `/` had nothing rendering it, since Nuxt's catch-all route never matches the root path. Fixed by extracting a shared `usePayloadPage` composable used by both `index.vue` and `[...slug].vue`.
2. **Build-time prerender vs. runtime CMS dependency** — `nitro.prerender.routes: ["/"]` tried to statically render the homepage during the isolated Docker build step, before any CMS is reachable; build failed with a 404. Removed.
3. **Internal vs. external API base URL mismatch** — `NUXT_PUBLIC_API_BASE=http://localhost:3001` resolved to the `web` container itself during SSR, not the CMS container, and port 3001 was never published to the host. Split into `apiBaseInternal` (server, direct to `cms`) and a relative `public.apiBase` (client, via Caddy).
4. **Payload CLI ESM/CJS incompatibility** — `payload migrate:create` crashed with `ERR_REQUIRE_ASYNC_MODULE` on both Node 20 and Node 24, traced to `@payloadcms/richtext-lexical`'s ESM build being `require()`'d by Payload's `tsx`-based CLI loader. Fixed by adding `"type": "module"` to `apps/cms/package.json`.
5. **Production-mode schema migrations** — Payload's Postgres adapter doesn't auto-sync schema in production; first real run threw `relation "pages" does not exist`. Fixed by generating a checked-in migration and running `npx payload migrate` in the Dockerfile's `CMD`.
6. **Caddy auto-HTTPS on localhost** — a bare `{$SITE_DOMAIN:localhost}` site block got a 308 redirect to HTTPS with an untrusted local CA cert. Fixed by parameterizing the scheme (`SITE_SCHEME`/`CMS_SCHEME`), explicit `http://` in dev.
7. **Shared `NODE_ENV` override** — see Secrets & Configuration above.
8. **TypeScript `Where`-type inference** — `Pages.ts`'s access-control function returned a union of differently-shaped object literals, which TypeScript couldn't reconcile against Payload's `Where` type despite each branch being individually valid; fixed with an explicit `as Where` cast per branch.
9. **Docker secrets-in-layer anti-pattern (caught before shipping)** — an initial attempt to pass `PAYLOAD_SECRET`/`DATABASE_URL` as Docker build `ARG`/`ENV` (to "fix" a CI failure that, on investigation, didn't actually exist) was reverted after Docker's own `SecretsUsedInArgOrEnv` linter flagged that this bakes secrets into the image's permanent layer history.
10. **`payload migrate:create`'s interactive prompt can't be scripted** — the create/rename-column disambiguation prompt (drizzle-kit's `hanji` library) creates a `readline.Interface` in line-buffered mode *and* layers raw keypress parsing on top of the same stdin; on a non-TTY stdin (any scripted `docker run -i`/`exec -i`, piped newlines, `yes ''`, CI) the two input paths conflict and it hangs regardless of how much input is piped in — traced to `node_modules/drizzle-kit/api.mjs`, not fixed by trying harder to script it. The same prompt appears in Payload's dev-mode schema push (`pushDevSchema` → drizzle-kit's `pushSchema`) whenever the live dev DB's schema differs enough from the code to be ambiguous. Real fix: run it from an actual terminal (`docker compose exec -it cms npx payload migrate:create <name>`), or avoid the ambiguity in dev by resetting the dev DB volume so there's nothing to disambiguate against.
11. **`@nuxt/ui`/`@nuxt/icon` were silently disabled the whole time** — both require Nuxt ≥4, but `apps/web` was pinned to Nuxt 3.21.11; Nuxt doesn't fail the build for an incompatible module, it just logs a `WARN [NUXT_B8013]` and disables it, so the modules appeared installed and configured but never actually ran. Fixed by upgrading `nuxt` to `^4.5.2` in both `apps/web` and the `polysite-theme-acme` layer (a layer's own Nuxt version mostly only matters for that repo's own tooling/typings — the consuming app's installed `nuxt` is what actually runs — but kept in sync to avoid future confusion). Nuxt 4.5.2 in turn requires Node ≥22, so both Dockerfiles moved from `node:20-alpine` to `node:22-alpine` (they are on `node:24-alpine`, the 24 LTS line, now; Dependabot is told to stay on LTS lines).
12. **Dev-mode bind mounts shadow build-time generated directories** — `docker-compose.dev.yml` bind-mounts the whole `apps/web` (and `apps/cms`) source tree over the image at runtime for hot-reload, which also overlays `node_modules` and Nuxt's `.nuxt` (generated by `nuxt prepare`) with whatever's on the host — nothing, since no Node runtime lives there. Fixed with named volumes mounted specifically at `node_modules` and `.nuxt` so those subpaths keep the container's own content instead of the (empty) host bind. `.nuxt` also has to be *regenerated* at container start (`npx nuxi prepare` in `CMD`, before `nuxt dev`), not just preserved from image build time — the dev stage's `npm install` runs before `nuxt.config.ts`/the theme layer are bind-mounted in, so its build-time `nuxt prepare` produces a `.nuxt` for what looks like an empty project.
13. **Payload's admin `importMap.js` doesn't hot-reload** — it's generated once (`payload generate:importmap`) and read at process start; adding a plugin or collection that registers a new admin component (e.g. `@payloadcms/plugin-seo`'s preview component) without regenerating it produces a runtime `getFromImportMap: PayloadComponent not found in importMap` warning in the admin UI, and regenerating the file alone isn't enough either — the running `next dev` process already has the old one loaded, so the CMS container needs a restart too.
14. **Docker Desktop host port-forwarding can go stale after a sleep/restart** — containers stay healthy (internal container-to-container `curl` returns instantly) but host-side `Invoke-WebRequest`/`curl.exe -4` to the published port hangs or times out. Restarting the affected containers didn't help; it resolved itself once traffic was addressed to `127.0.0.1` explicitly rather than `localhost` (which was resolving to `::1` first). Caveat found later: `127.0.0.1` only works for hitting a container's own published port directly (`cms:3001`, `web:3000`). Caddy virtual-hosts on the `Host` header (`localhost`/`admin.localhost`), so a bare `curl http://127.0.0.1/...` gets an empty `200` from Caddy (no matching site block) — test through Caddy with `curl --resolve localhost:80:127.0.0.1 http://localhost/...` instead, which keeps the correct `Host` header while still forcing IPv4.
15. **Vite's dev-server file watcher never fires on Windows bind mounts** — `docker-compose.dev.yml` bind-mounts `apps/web` from the Windows host, and Docker Desktop doesn't propagate native filesystem change events into the Linux container, so chokidar's default (inotify-based) watcher silently never triggers HMR — edits kept serving stale component output until the container was restarted, confirmed by editing `TextBlock.vue` and watching the response not change. Fixed with `vite: { server: { watch: { usePolling: true } } }` in `nuxt.config.ts`; pure dev-server config, so it's a no-op for `nuxt build`/production.
16. **`[...slug].vue` crashed on an unguarded `livePage.title`** — `useLivePreview`'s `data` ref can transiently be `undefined` (Nuxt 4's `useFetch`/`useAsyncData` default to `undefined` instead of `null`, a real behavior change from the Nuxt 3→4 upgrade), and the template read `livePage.title`/`livePage.content` without optional chaining on `livePage` itself, throwing `Cannot read properties of undefined (reading 'title')` client-side. Fixed with `livePage?.title` / `livePage?.content?.length` / `livePage?.content`.
17. **`usePayloadPage`'s `useFetch` call needed an explicit, slug-based key** — its auto-generated cache key is derived from the request URL string alone (`${base}/pages`), which is identical for every slug; a client-side navigation from one page to another (e.g. homepage → `/about-us`) reused the first page's cached response instead of refetching, so the second page always 404'd. Reproduced for real: browsing in-app from `/` to `/about-us` 404'd every time, while a fresh full page load of `/about-us` (curl, or a new tab) worked fine. Fixed by passing `key: \`payload-page-${slug}\`` to `useFetch`.
18. **Payload's default logout control is icon-only** — `@payloadcms/ui`'s `Logout` component renders just `<LogOutIcon />`; the "Log out" text only exists as an `aria-label`/`title` tooltip, invisible at a glance. Real user-reported confusion ("no logout button found") despite the control being right there in the nav. Fixed with a custom `apps/cms/src/components/LogoutButton.tsx` wired in via `admin.components.logout.Button`, adding a visible text label next to the icon — same underlying link/href, just with the label rendered instead of hidden in the accessible name alone.
19. **Two collections had real, unrestricted access-control gaps, not just missing role distinctions** — `Sites` defined `create`/`update`/`delete` but never `read`, which defaults to Payload's built-in `() => true`: every Content Editor and Campaign Manager (and any unauthenticated API caller) could list every client's Sites record regardless of `assignedSites`. `Media` defined only `read`, so `create`/`update`/`delete` also defaulted wide open: any authenticated user, any role, any site, could upload or delete any site's files. Fixed by adding proper site-scoped access functions to both (`Media` also gained a `site` relationship field it never had), extracted into a shared `apps/cms/src/access/roles.ts` (`isAdmin`, `isAdminOrCampaignManager`, `userSiteIds`) alongside the pre-existing Pages.ts/Commitments.ts pattern.
20. **Content Editor vs. Campaign Manager had no actual behavioral difference anywhere** — both roles hit the exact same site-scoped access functions on every collection; the product requirements name them as distinct personas ("Campaign Manager... manages form layouts" vs. "Content Editor... drafting articles") but nothing in code reflected that. Payload has no built-in RBAC admin UI — access control is purely code-defined functions per collection/field (confirmed against Payload's own docs and its "build your own RBAC" guide, which uses this exact pattern: a `role` field plus functions returning booleans or `Where` filters). Implemented this boundary: Content Editor can create/edit Pages/Commitments/Media but can't set a Page's `status` to `published` (field-level `access.update`/`access.create` on that one field — Payload silently reverts a denied field write rather than failing the whole save, verified for real: an editor's `POST` with `status: "published"` came back saved as `"draft"`); Campaign Manager can do everything Editor can, plus publish and manage the form-builder plugin's `Forms`/`Form Submissions` collections (overridden via `formBuilderPlugin`'s `formOverrides`/`formSubmissionOverrides`, since the plugin's own defaults have no restriction at all). Verified end-to-end against the project's actual 3 user accounts, not just the logic in isolation: editor sees 1 of 2 sites, editor's publish attempt reverts to draft, editor is denied `Forms` entirely, campaign-manager can read `Forms` and successfully publish.
21. **A real ccTLD pointed at loopback gets its scripts silently blocked by the browser** — tried naming local dev domains `local.polysite.ca`/`local.voidslate.ca` (hosts file entries to `127.0.0.1`), which is a legitimate DNS setup (`Resolve-DnsName` confirmed it resolved correctly) but broke in the browser anyway: every `_next/static/chunks/*` (and Nuxt's `_nuxt/*`) request came back `ERR_BLOCKED_BY_CLIENT`, reproduced independently in two separate browsers, while the exact same files loaded fine from `localhost:3001` directly and via `curl` through Caddy on the `.ca` domain. The document itself always loaded (server-side everything was correct); only client-side script/style requests were blocked. Root cause: a real-looking public TLD resolving to loopback over plain HTTP matches a phishing/malware-evasion heuristic that browser and OS-level security layers (Windows network protection, AV web-shields, some content blockers) specifically watch for, and `localhost`-pattern hostnames are the well-known, deliberate exemption from it. Fixed by switching to `*.localhost` subdomains (`polysite.localhost`/`voidslate.localhost`) instead of a real ccTLD — per RFC 6761 every browser auto-resolves any `*.localhost` name to `127.0.0.1` with no hosts file entry at all, and treats it as a trustworthy local origin, avoiding the heuristic entirely rather than needing to whitelist anything.
22. **Two pages with the same slug on different sites, or a URL not scoped to the requesting domain at all** — `usePayloadPage`/`useCommitments` queried by `slug` alone, globally, with no awareness of which `Site` a request's domain belongs to; with only one Site in the dev DB this never surfaced, but it's the exact multi-tenant gap the product requirements call out. Fixed by resolving the current `Site` from the request's own hostname (`useRequestURL().hostname`, isomorphic — works identically during SSR and client-side navigation) and filtering both queries by the related Site's `domain` field via Payload's relationship dot-notation query (`where[site.domain][equals]`). Also added a `validate` function on `Pages.slug` rejecting a second page on the *same* site reusing a slug (a different site reusing the same slug is fine and expected). Two real things caught while building this: (1) the relationship-field query initially failed with `"cannot be queried: domain"` — Payload's query-path validator requires *read access on the joined collection*, not just the collection being queried, so `Sites`' anonymous-read-denied fix from Known Issue #19 had to be loosened back to public read (site `name`/`domain` aren't sensitive; the real leak that issue fixed was cross-site visibility between authenticated non-admin users, which is unaffected). (2) Caddy itself only routes the single `SITE_DOMAIN` from `.env` — verified a genuinely second site's isolated content resolves correctly by querying the web container directly with `curl --resolve <domain>:3000:127.0.0.1`, bypassing Caddy, since testing a real second domain through Caddy needs a site block added for it first (see Not Yet Built).
23. **The homepage silently ignored its own CMS content** — the admin's Home page (slug `/`) points at the actual homepage, but editing it did nothing, because the theme's `pages/index.vue` was a fully hardcoded template (header, hero+signup, leader spotlight, commitments, donation tiers, footer) that only ever read the page's `title` field — its `content` blocks were never rendered at all, unlike every other page (`[...slug].vue`, which renders `content` via `BlockRenderer`). Fixed by making the homepage genuinely block-driven: four new block types (`SignupForm`, `LeaderSpotlight`, `DonationTiers`, `CommitmentsGrid` — at the time, a marker with no data field of its own, rendering the current site's Commitments collection; converted to inline items in Known Issue #26) plus matching frontend components, and `pages/index.vue` simplified to the exact same `usePayloadPage`/`useLivePreview`/`BlockRenderer` logic as `[...slug].vue` (it only still exists as a separate file because Nuxt's `[...slug].vue` catch-all doesn't match the bare root path — not because the homepage needs different rendering). A second inconsistency surfaced while fixing this and got fixed too: only the old hardcoded homepage had a header/footer at all — every other page had no navigation whatsoever. Added a site-wide `layouts/default.vue` (applied via `<NuxtLayout>` in `app.vue`) so navigation is consistent on every page, not just `/`.
24. **`Hero.image` was a real, populated field that the frontend never rendered** — updating the Hero block's image in the admin had no visible effect on the homepage. Confirmed via the API that the field really was set and populated correctly (Payload returns the full `Media` doc, including `url`, at `depth: 1`) — `HeroBlock.vue` simply never declared an `image` prop or rendered it at all, for any page, since the block was first built. Not a caching or reactivity bug; the prop didn't exist. Fixed by adding the prop and rendering it as a full-width banner image with the heading/subheading overlaid when present, falling back to the original plain layout when a Hero has no image (most existing ones don't).
25. **`@payloadcms/plugin-seo`'s `meta.title`/`meta.description`/`meta.image` fields were real and populatable but never read by the frontend** — same defect class as #24, found by an explicit audit of every block after that one turned up (every block itself turned out clean; this was found checking the adjacent SEO fields while at it). `index.vue`/`[...slug].vue` only ever called `useHead({ title: ... })` off the plain `title` field — the SEO plugin's admin tab (title/description/meta image, with its own character-count checks) had zero effect on the actual rendered `<head>`, latent since no page had used it yet. Fixed with a shared `usePageSeoMeta` composable (`useSeoMeta`, reactive against Live Preview) applying `meta.title`/`meta.description` with a fallback chain to the plain `title` field (matching the plugin's own `generateTitle` fallback behavior in the admin), plus `og:title`/`og:description`/`og:image` — the last resolved to an absolute URL via `useRequestURL().origin`, since Payload's upload `url` is relative and Open Graph crawlers need an absolute one. Verified for real: set `meta.title`/`meta.description` on a page via the API, confirmed `<title>`, `og:title`, `name="description"`, and `og:description` all update in the rendered HTML; confirmed a page with no meta set still falls back to its plain title correctly.

26. **`Commitments` was a full collection (with its own RBAC surface) for what was really just a list of cards on one block** — it has a handful of text fields (heading, body, link button) per card, no reason to be a separate collection, its own admin nav entry, or its own site-scoped access functions when `FeatureGrid` already does the same "heading + array of cards" shape inline on the block itself. Converted `CommitmentsGrid` from a marker block (Known Issue #23) into one with its own `items` array field (heading, body, `ctaLabel`, `ctaHref` per item), removed the `Commitments` collection, its access-control functions, its `onInit` seeding, and the `useCommitments` composable entirely. Zero data loss: the 6 live cards were fetched via the API first and re-saved into the Home page's new `commitmentsGrid.items` array before the collection was dropped, verified end-to-end by a fresh browser render of the homepage afterward. Hit Known Issue #10's interactive schema-push prompt twice, in two different shapes, doing this: (a) adding the new `items` array field alone produced drizzle-kit's create-vs-rename disambiguation prompt for the new junction table (`pages_blocks_commitments_grid_items`) — resolved by staging the change (add the new field while `Commitments` still existed, so the new table was an unambiguous pure addition, confirmed via `docker logs` showing no prompt); (b) removing the `Commitments` collection afterward produced a *different* prompt, a plain `prompts`-library data-loss confirmation (`You're about to delete commitments table with 6 items... Accept warnings and push schema to database? (y/N)`) that silently defaults to declining when piped/non-interactive (confirmed via `psql` that the table survived a piped "yes"). Since the data had already been preserved via the API, this one was resolved by bypassing Payload's push tooling entirely and running `DROP TABLE IF EXISTS commitments CASCADE;` directly against the dev Postgres container — a new variant of the same root prompt-can't-be-scripted problem, worth recording since it isn't the rename-ambiguity prompt Known Issue #10 originally described.

27. **The header's `Menu` button was a bare `<button>` with no click handler and no nav markup behind it at all** — on the homepage, clicking it did nothing, anywhere on the site, since the site-wide layout added in Known Issue #23 only ever rendered `<button class="btn btn-outline" type="button">Menu</button>` with no `@click`, no toggled state, no drawer/dropdown markup to show — purely decorative from the moment it was added. Fixed in `themes/polysite-theme-acme/layouts/default.vue` with a `menuOpen` ref toggled on click (`aria-expanded`/`aria-haspopup`/`aria-controls` wired to match) and a dropdown `<nav>` listing the same pages already linked from the footer (Leader, Our Team, About Us, Our Platform, Take Action, Volunteer, FAQ, Become a member). Verified in a real browser: clicking Menu shows the 8 nav links, clicking it again hides them.

28. **Tailwind CSS v4's zero-config automatic content detection silently skips the theme layer, because it's a nested independent git repository** — added Tailwind (already available via `@nuxt/ui`'s own dependency, see Theme Layer above) plus a site-level branding config (`Sites`' new "Branding" tab: logo, favicon, colors, header nav, footer columns, social links) and a full visual restyle of the homepage's blocks. Utility classes used only in `themes/polysite-theme-acme/layouts/default.vue` (`w-80`, `ml-auto`, `z-40`, `z-30`, and any arbitrary `bg-[var(...)]` value) generated **no CSS at all** — confirmed for real by fetching the compiled `main.css` and searching for their selectors directly, not just eyeballing the page. Classes that happened to *also* be used elsewhere in the app (`flex`, `h-full`, `p-6`, `rounded-full`, `sticky`, ordinary `z-10`/`z-20`/`z-50` from unrelated components) appeared to work, which was pure coincidence and nearly masked the real bug. Root cause: Tailwind v4's automatic source detection walks the project respecting every `.gitignore` it finds and treats a nested `.git` boundary the same way it treats `node_modules` — an exclusion zone — and `themes/polysite-theme-acme` is exactly that (its own independent git history, deliberately not tracked by the core repo; see its README). Fixed with an explicit `@source "../../../../themes/polysite-theme-acme";` directive in `apps/web/assets/css/main.css`, which brings the theme layer back into Tailwind's scan regardless of the automatic heuristic. Verified by fetching the compiled CSS again and confirming all four previously-missing selectors were present, then confirming the drawer/colors rendered correctly in a real browser.

29. **Migrated from hand-rolled site-scoping to `@payloadcms/plugin-multi-tenant`** — pulled forward from its original place after the first deployment (see Modules & Plugins above). Kept `Sites`' existing slug/name and the `site` field name on `Pages`/`Media` instead of the plugin's own `tenants`/`tenant` defaults (`tenantsSlug: "sites"`, `tenantField: { name: "site" }`) — this meant the frontend (`usePayloadPage`, `useSite`, every `site.domain`/`site` query) needed **zero changes**; only the access-control internals changed, not the public data shape. `Sites.ts` keeps its own hand-written access control (`useTenantsCollectionAccess: false`) since it already had a carefully-reasoned policy (Known Issue #19/#22); `Pages.ts`/`Media.ts` had their manual `{ site: { in: userSiteIds(user) } }` `Where` filters removed entirely — the plugin ANDs that same constraint on automatically via `useTenantAccess` (default), and admins skip it via `userHasAccessToAllTenants: (user) => isAdmin(user)`. `Users.assignedSites` changed from a hand-written flat `hasMany` relationship to the plugin's own array field (`tenantsArrayField`, same outer name kept) — `userSiteIds()` in `access/roles.ts` updated for the new nested row shape (`user.assignedSites` is now `[{ site: <id> }]`, not `[<id>]`).

    Hit Known Issue #10's interactive schema-push prompt twice more, both new variants: (a) `users_assigned_sites` (the plugin's new array-field table) triggered the same create-vs-rename disambiguation as Known Issue #26's first prompt — resolved by inspecting an already-clean sibling array table (`sites_header_nav_items`) to learn Payload's exact column convention (`id` a bare `character varying` primary key with no default, `_order`/`_parent_id` integer, one column per row field) and creating `users_assigned_sites` directly via SQL to match it exactly, after backing up the 2 real user→site assignments via the API first. Restarting then cleanly resolved that ambiguity (the table already existed matching expectations) and immediately hit (b): a data-loss confirmation for dropping `users_rels` (Payload's old shared relationship-storage table, now orphaned since nothing references it through that mechanism anymore) — verified via `psql` that its 3 rows were exactly the assignments already preserved, then dropped it directly, same bypass pattern as Known Issue #26's second prompt. Verified end-to-end afterward: `GET /api/pages/1` still returns `"site":1` untouched, the content editor's "Assigned Sites" array field renders "Dev Test Site" correctly in the admin (proving the SQL-inserted row round-trips cleanly through Payload's own UI, not just the raw table), the public frontend renders with zero changes needed, and a non-admin login still sees exactly their assigned site's pages.

30. **Per-site theme selection: multiple theme repos extended into one build, chosen dynamically by `Sites.theme` at runtime — not a new container per theme** — a deliberate decision after weighing the trade-off: a separate frontend deployment per theme (the closest analogue to how real multi-brand Nuxt/Next sites on a headless CMS are usually run) was rejected as infeasible to keep spinning up by hand, and "just recolor one shared layout" wasn't enough either, since a genuinely new client needs a structurally different design, not just different colors on the same header/footer shape — which per-site branding data (Known Issue #28) already covers on its own. Landed on the pattern WordPress Multisite uses conceptually (every theme's files present at once, a per-site setting picks which one renders) adapted to what a *compiled* Nuxt app can actually do: WordPress can `require` a different theme's PHP files fresh per request because it's interpreted with no build step; Nuxt can't do that, but it can merge multiple Nuxt layers into one build and pick between their *named* layouts at runtime, which is the mechanism actually used here.

    `Sites` gains a `theme` select field (`acme` / `bakery`, extensible). `apps/web/nuxt.config.ts`'s `extends` lists every theme repo simultaneously, not one per deployment. Each theme names its layout file after itself (`layouts/acme.vue`, `layouts/bakery.vue`) instead of Nuxt's `default.vue` convention — required, since two themes both using `default.vue` would collide and only one would win when merged into the same build. `app.vue` resolves which one renders per request: `<NuxtLayout :name="site.theme || 'acme'">`, driven by the same `useSite()` hostname resolution every other per-site feature already uses. Adding a new theme later means adding its repo path to `extends` (plus a Dockerfile `COPY` line and a dev-compose bind mount — see the Docker build implication note above) and redeploying `web`; it never means a new container or Caddy route, since one running app already contains every theme's code.

    Two pieces of cleanup fell out of doing this for real, not just adding a second theme: (a) `pages/index.vue` used to live inside the theme repo, but its logic was already 100% theme-agnostic (identical to `[...slug].vue`, separate only because of Known Issue #1's routing gap) — two themes both shipping a `pages/index.vue` would have collided on that file path the same way `default.vue` would have, so it moved into the core app permanently, closing that latent trap before it could bite. (b) the branding-data wiring (colors/fonts/nav/footer/social-link fallbacks) that used to live inline in the one theme's layout got extracted into a shared `useSiteBranding()` composable, since every theme needs it identically and duplicating it per theme risks the copies drifting.

    Hit one real bug building this, not caught until a second theme actually existed to exercise the shared-composable path: the first version of `useSiteBranding()` was `async`, doing `const site = await useSite()` internally before calling `useHead()` — worked fine for the single existing theme (the exact same `await`-then-`useHead()` shape it was extracted from), but produced a real 500 ("A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function") once `layouts/bakery.vue` called it. Root cause: Vue's async-`setup()` support restores a component's Nuxt-instance context automatically across an `await`, but only for the setup function's *own* top-level await — not one buried inside a separate function that setup merely calls, even when that whole call is itself awaited. Fixed by making `useSiteBranding()` synchronous, taking the already-resolved `site` ref as a parameter instead of fetching it internally; each theme's layout now does `const site = await useSite()` directly in its own `<script setup>` (a real top-level await, the same proven-safe pattern `usePayloadPage` already used in `[...slug].vue`) and passes the ref into the now-synchronous helper. Verified end-to-end: both themes render simultaneously from the same running `web` container (`voidslate.localhost` → `acme`'s sticky pill-button header, `bakery.localhost` → `bakery`'s centered masthead with a utility bar and wrapping inline nav), each with its own real per-site colors, and the original theme's Menu drawer still opens/closes correctly — confirmed via computed styles and DOM queries in a real browser, not just a visual glance.

31. **More per-site theme settings (tagline, hide-the-Donate-button) plus Custom CSS/JS fields — and a real finding about this app's actual CSP, not the one its own comments assumed** — WordPress-style theme management was an explicit requirement (settings + file editing), which prompted a direct comparison: WordPress's Theme File Editor writes PHP that executes on the server with no compile step, and is widely recommended to *disable* for exactly that reason (`DISALLOW_FILE_EDIT`) — there's no safe equivalent for a compiled Nuxt app, so that half was declined in favor of two lower-risk, still-genuinely-useful pieces: more granular `Sites` settings (`tagline`, `showDonateButton`, both wired through `useSiteBranding()` into both themes' layouts), and raw `customCss`/`customJs` textareas injected site-wide from `app.vue`.

    `customCss` is low-risk (CSS can't execute server-side code). `customJs` is not — it genuinely executes in every visitor's browser, so it's admin-only by Sites' own existing access control and *only* as safe as that access control, full stop; if it were ever loosened to Content Editor/Campaign Manager, this becomes a real stored-XSS vector, not something CSP additionally catches (see why, below).

    Assumed initially, then checked for real rather than left as an assumption: that `nuxt-security`'s default strict-dynamic CSP would auto-attach its nonce to `useHead()`-injected inline `<script>`/`<style>` tags during SSR, the way its own docs describe for "SSR mode." **Confirmed false for this specific injection path** — fetched the actual `Content-Security-Policy` response header (`curl -I`) and inspected the rendered DOM: the injected tags carry no `nonce` attribute at all. What's actually permitting them to run is `'unsafe-inline'`, already present in this app's CSP (`script-src 'self' https: 'unsafe-inline' 'strict-dynamic' 'nonce-...'`) as a pre-existing fallback, unrelated to and unchanged by this feature — not nonce-gating. Corrected the code comment that had claimed otherwise before it could mislead a future session into overstating this field's actual security posture. No CSP config change was needed either way, since `'unsafe-inline'` was already there — but *why* it works turned out to be different from the first (unverified) assumption, worth recording precisely rather than leaving the more reassuring-sounding wrong explanation in place.

    Verified end-to-end in a real browser: `customJs` executing (a `console.log` marker appeared, confirmed via `read_console_messages`), `customCss` applying (computed style changes), `showDonateButton: false` correctly removing the button from the DOM (not just hiding it visually) on the site it was set on while the other site's button rendered normally (field unset, default `true`), and the `tagline` rendering next to the wordmark on both themes' layouts.

32. **WordPress-style theme auto-discovery — the `Sites.theme` dropdown and `nuxt.config.ts`'s `extends` array both scan `themes/` at boot instead of a hand-maintained list** — Known Issue #30 shipped `theme` as a hardcoded Payload `select` with two literal options; a hand-maintained list, even one moved into its own file, is not auto-discovery, just tidier hardcoding. What they actually wanted, stated explicitly: scan the theme directory, find a specific marker file, list every valid theme, the way WordPress does with `style.css`'s header block.

    The real obstacle: `cms` and `web` are separate containers, and `themes/` was previously mounted into neither the CMS's build context nor its runtime container at all — the CMS had zero filesystem visibility into theme files before this. Fixed by widening `cms`'s Docker build context from `./apps/cms` to the repo root (mirroring `web`'s existing pattern) and mounting `themes/` read-only into the dev container. A directory `themes/polysite-theme-<value>/` now counts as a valid, listable theme when it has both `layouts/<value>.vue` (proves it's actually wired to render — the same naming convention Known Issue #30 already established) and a `theme.json` with a `label` (the WordPress `style.css`-header equivalent; a raw directory name isn't a presentable label on its own). `apps/cms/src/collections/Sites.ts`'s `discoverThemes()` and `apps/web/nuxt.config.ts`'s `discoverThemePaths()` run the identical scan independently — not shared code, since `apps/cms` and `apps/web` are separate Next.js/Nuxt projects with no monorepo package-linking set up, and forcing a literal cross-app import risks the same class of build-boundary failure this project has hit before (Known Issue #9 and others) for a problem ~25 lines of duplicated `fs`/`path` code solves at near-zero risk.

    A real bug caught during implementation, before it shipped: the CMS Dockerfile's `run` stage originally kept its pre-existing flat `WORKDIR /app` structure while the `build` stage moved to `/repo/apps/cms` — `Sites.ts` resolves the scan directory via `path.resolve(process.cwd(), "../../themes")`, so the `run` stage's shallower path would have silently resolved to `/themes` instead of `/repo/themes`, missed every real theme, and fallen back to the hardcoded single-theme default with no visible error. Fixed by keeping `/repo/apps/cms` as the `run` stage's `WORKDIR` too, matching the `build` stage exactly.

    Also simplified the Dockerfiles/compose files from one `COPY`/bind-mount line per theme to a single `COPY themes themes` / `./themes:/repo/themes` covering the whole directory — a real consequence of moving to scanning: per-theme infra lines would have meant the scan finding a theme that Docker never actually shipped into the image, a worse failure mode than today's explicit per-theme lines. Confirmed nested theme repos' own `.git` directories are excluded from the image by the existing root `.dockerignore`'s bare `.git` pattern (matches at any depth, same semantics as `.gitignore`) before relying on it.

    Verified end-to-end in a real browser after a full rebuild of both containers: the CMS admin's Theme field description itself now reads "Auto-discovered from themes/ at boot (2 found: bakery, acme)", the dropdown shows both correctly-labeled options ("ACME-style", "BAKERY-style") read live from each theme's `theme.json`, and both sites' frontends still render exactly as before (real per-site colors, ACME's Menu button, BAKERY's tagline) — a pure refactor of *how* the lists are built, zero functional regression.

All three were fallbacks for the *same* "found nothing to discover" edge case Known Issue #32's scan already had to handle: `apps/cms/src/collections/Sites.ts`'s `discoverThemes()` returned `[{ label: "ACME-style", value: "acme" }]` (twice — the `themes/` unreadable case and the zero-valid-themes case) and used it again in `defaultValue: THEMES[0]?.value ?? With that in place, every fallback above changed from a specific client's name to `"default"`: `Sites.ts`'s two array fallbacks and its `defaultValue`, `nuxt.config.ts`'s two `extends`-array fallbacks (now correctly returning `[]` rather than forcing a nonexistent-in-a-fresh-clone theme path — an empty `extends` is fine now that `layouts/default.vue` covers the no-theme case on its own), and `app.vue`'s `site.theme || "default"`.

    Verified end-to-end in a real browser after restarting `cms`/`web`/`caddy`: both existing Sites (`acme`, `bakery`) kept their explicit theme values and render unchanged (ACME's pill-button header, BAKERY's masthead, both fully styled — confirming the `@source` glob fix didn't regress either theme); the CMS admin's Theme field description still correctly reads "Auto-discovered from themes/ at boot (2 found: bakery, acme)" with no `acme` string hardcoded into that output itself, only genuinely discovered.

34. **RBAC replaced with a fully dynamic system — roles are data, not a hardcoded enum** — a deliberate design decision: Polysite is being built as a bigger, productized platform, and new collections will keep getting added over its life, so who can do what shouldn't require a code deploy every time. Landed on a genuine `roles` collection (`apps/cms/src/collections/Roles.ts`) a Super Admin creates/renames/reconfigures entirely through the admin UI. Two deliberate design choices came out of the discussion, both correcting an earlier draft: (a) **general operations, not per-collection permissions** — a role has one flat `operations` set (create/read/update/delete/publish/unpublish/cloneAcrossSites) applied *uniformly* to whichever `modules` (collections) it's given, rather than a separate permission grid per collection; a future collection (Events, etc.) only ever needs adding to `apps/cms/src/rbac/modules.ts` and to an existing role's `modules` list — no new permission definitions, ever. (b) **the first two 4-role drafts were rejected** — Content Manager and Content Creator, initially proposed with different capabilities, were merged into one **Site User** role after it was pointed out (with a concrete example: "content creator can also create forms, and read form submissions") that the drafted split didn't reflect a real distinction. Final set is 3 roles: **Super Admin** (see below), **Site Admin** (full content operations + `manageSiteSettings: true` — can edit its own assigned Site's branding/theme/domain/custom CSS-JS), **Site User** (identical to Site Admin minus `manageSiteSettings`).

    One deliberately **non**-dynamic piece: `Users.isSuperAdmin`, a plain boolean, checked before any role lookup at all. The aim was zero hardcoding anywhere, but this one exception should stay: if Super Admin access were itself governed by the same dynamic `roles` lookup, a corrupted or misconfigured role document could lock every admin out of the one collection that could fix it, or be used to self-escalate. Same pattern as WordPress Multisite's network Super Admin list (stored separately from per-site roles/capabilities) or AWS's root account sitting outside IAM policy evaluation entirely — not a role, an escape hatch. The "Super Admin" *role* document still exists (pre-seeded, `isDefaultDeployed: true`) for UI/assignment purposes, but it grants nothing by itself; only the flag does.

    A capability check (`hasCapability(user, moduleSlug, operation)` in `apps/cms/src/access/roles.ts`) runs on every request, so it reads from an in-memory cache (`apps/cms/src/rbac/permissionCache.ts`) rather than querying `roles` each time — populated once at boot (`onInit` in `payload.config.ts`) and invalidated live by `Roles.ts`'s own `afterChange`/`afterDelete` hooks, so a Super Admin editing a role's permissions takes effect on the very next request, no restart. **Default-deny at every branch, on purpose** — a missing role, an unlisted module, or an unchecked operation all resolve to `false`, the same discipline Known Issue #19's real gap (an undefined access function defaulting to Payload's own `() => true`) already forced onto this codebase once; verified for real by editing "Site User"'s live role to drop `pages` from its module list and confirming Pages write access was genuinely rejected, immediately, with zero restart, then restoring it.

    Three collateral pieces landed alongside the core system: (a) a per-Site `enabledModules` field on `Sites.ts` — data-only for now (Pages/Media/Forms aren't independently routable, so there's nothing yet for the frontend to gate; becomes load-bearing once a second standalone-routable content type exists), distinct from a role's own module access (a role *can* touch Forms; whether a given *site* has Forms turned on is separate). (b) Hiding `@payloadcms/plugin-multi-tenant`'s "Filter by Tenant" selector from every non-Super-Admin role ("no traces of it" was the requirement) — the plugin's config has no per-role visibility option at all (confirmed by reading its source, `dist/index.js`: it pushes `TenantSelector` into `admin.components.beforeNav` unconditionally at config-build time, before any request/user context exists), so `payload.config.ts` runs a small plugin *after* `multiTenantPlugin` that swaps that one `beforeNav` entry for `apps/cms/src/components/TenantSelectorGate.tsx`, which renders the real selector only when `isSuperAdmin` is true. (c) A cross-site Page clone action (`POST /api/pages/:id/clone`, a custom Payload endpoint on `Pages.ts`, triggered from a "Clone to another site" item in the same `editMenuItems` 3-dot-menu slot the multi-tenant plugin uses for its own "Assign Tenant" action) — available to Site User and above, server-side enforced (capability + target-site membership checked in the endpoint itself, never trusting the client), always lands as a **draft** on the destination site regardless of the source's status (standard content-staging safety default).

    Three real bugs hit and fixed while building this, all confirmed rather than assumed: (1) both new admin components (`TenantSelectorGate`, `CloneToSiteButton`) needed `payload generate:importmap` plus a full container restart before Payload's admin would render them — the exact same failure mode as Known Issues #13/#18 (`getFromImportMap: PayloadComponent not found`), hit again here because it's a structural limitation of Payload's admin, not something those earlier fixes could have prevented for future components. (2) The clone endpoint's first version copied a source Page's `content` blocks verbatim, including their own `id`s — Payload's Postgres adapter stores each block type in its own table with `id` as a real, globally-unique-within-that-table primary key, not scoped per parent document, so the create failed with `"Value must be unique"` on `id`. Fixed with a recursive `stripIds()` that drops every nested `id` before the clone's `create` call, letting Payload assign fresh ones — same as if an editor had built the page from scratch. (3) The clone trigger's first version tried to expand an inline site-picker form directly inside the `editMenuItems` popup slot — Payload's own popup menu closes on any click inside it, so the inline expansion never got a chance to render, the same reason `@payloadcms/plugin-multi-tenant`'s own "Assign Tenant" action is a *modal*, not an inline expansion, in its own source. Fixed by rendering the picker via a React portal straight into `document.body`, decoupled from the popup's lifecycle.

    The migration itself hit Known Issue #10's interactive schema-push prompt again (a new `roles` table, a new enum, and `users.role` changing from a `select` to a `relationship` all needed confirmation) — this time resolved deliberately rather than by guessing, since real dev content (a client's actual brand colors, demo Pages) was at stake: backed up via `pg_dump` first, then wiped the dev schema clean (`DROP SCHEMA public CASCADE`) by decision, letting the push run against nothing-to-disambiguate, then recreated the 3 dev accounts/2 sites/2 homepages via a new idempotent seed script (`apps/cms/scripts/seedDevData.ts`) rather than hand-restoring from the dump. A real bug caught writing that seed script, not the migration itself: `payload run <script>` awaits the script module's own dynamic `import()`, and a fire-and-forget `run().catch(...)` at the bottom (no top-level `await`) let that `import()` resolve immediately — the whole process exited via `payload run`'s own wrapper before any of the script's `async` body had actually executed, silently producing zero output and zero data. Fixed by making the script's top-level body itself `await`-driven, keeping the module's own evaluation (and therefore the `import()` promise) pending until the seed genuinely finished.

    Verified end-to-end in a real browser as all three roles (the 3 existing dev accounts remapped: `admin@dev.local` → Super Admin, `campaignmanager@dev.localhost` → Site Admin, `contenteditor@dev.localhost` → Site User): Super Admin sees the tenant selector and the Roles collection with full write access, Site Admin can edit its assigned Site's settings and neither sees any multi-tenant UI, Site User can create/publish/unpublish Pages but gets no Save button at all on Sites, a live role edit (removing then restoring a module) took effect instantly with no restart in either direction, and a real Page clone from Dev Test Site to BAKERY Demo Site landed correctly as a fresh-id'd draft with a disambiguated slug.

59. **Two things that hang a boot or a sign-in, found building the auth plugin.** (1) A write from inside a sign-in hook to the user's own row waits forever: Payload holds a transaction that has already touched that row (it records the session first), and a write on another database connection queues behind it. Code in a login hook must pass `req` (join the transaction) for anything on the user row, and anything that has to survive a refused sign-in (a count of wrong codes, since the refusal rolls the transaction back) belongs in a table of its own, written without `req`. (2) In development, Payload's schema push asks for confirmation before dropping a column, and a container has no keyboard, so boot waits (about five minutes) and the first request after it appears to hang. After removing a field in dev, drop the column by hand or set `POLYSITE_DB_PUSH=false`. Related: `beforeLogin` runs after the password was checked and after a session was created, so a refusal there leaves an unused session record that expires with the rest; password reset signs the person in without running `beforeLogin` at all, which is why the auth plugin removes that session for accounts with two-factor on.
60. **A database write that names one array field silently empties the row's other array fields.** Found while building single sign-on: `payload.db.updateOne` rewrites every array table of a row from the data it is given, so writing only `sessions` removed the user's `assignedSites` (their site access) and the linked sign-in identities, and writing the identities removed the sessions. Payload avoids this because its own session write passes the whole user document. Anything that touches an array on a document through the adapter must do the same: read the full document (with hidden fields) and write it back with the one change (`saveWithArrays` in the auth plugin; `createSession` in the core). Plain values (flags, counters, text, JSON) are safe to write alone. The auth plugin's end-to-end checks now assert that `assignedSites` survive sign-in, reset and single sign-on. Related: the fresh-install smoke test now waits for both containers' Docker health checks before it starts, because the server answers a moment before the database is migrated and a test that started in that gap failed once for no real reason.

63. **The i18n plugin: several languages on a site, and what it took to get the public side right.** Design and research in the internal multilingual notes; editor guide in `docs/guide/languages.md`, plugin notes in `plugins/i18n/README.md`. Things that are not obvious: (1) **Where the pieces live.** The core web app is language-aware by itself (`utils/language.ts`: a language is the first path segment, only for a language the site offers, never for its default; `useSiteLanguage()`, `useLocalePath()`, `useT()`), because pages and links are the core's; the plugin supplies the settings (its own `site-languages` collection, read by the core as the contract key `site.extensions.languages`; Issue #64), the admin picker and list column, the switcher, `hreflang`/`noindex` and the dictionaries. A site with nothing set answers "English, no prefix" and no link or query changes. (2) `useSite()` reads the site in English first (that also says which languages it offers) and only reads it again in another language when the address asks for one or the site's own default isn't English, so a one-language site still makes one request. Composables must be called before the first `await` (Nuxt loses the request afterwards); the language state is captured at the top. (3) **`<html lang>` cannot be set from the page.** The SEO modules write it from the site configuration with a priority that no `useHead` option reliably beats (a numeric sweep either lost to "en" or dropped the attributes altogether), so `app.vue` records the language on the request and `server/plugins/htmlLanguage.ts` rewrites `lang` and `dir` at the very end of rendering; `updateSiteConfig` also gets the language so `og:locale` and the canonical address agree. (4) **Required translatable fields.** Payload validates a required localized field in whichever language is being saved, so the first French save of a page failed until every required block field had a French value. `relaxRequired` (`i18n/localize.ts`) removes `required` and re-adds it as a validation that applies only in the site's default language (`isDefaultLanguageHere`, which reads the site's `extensions.languages` through `i18n/registry.ts`); the columns become nullable (migration `i18n_plugin`). Plugins use the same through `kit.i18n.localizeNamed`. (5) **Which languages a page has** is kept on the URL index (`site-urls.languages`, filled in `beforeSync`), and the sitemap, the switcher and `hreflang` read it; the search plugin writes index entries only for languages a site offers (`skipSync` through the same registry), otherwise every page would get an entry per catalog language. (6) The admin language picker follows the site an editor is working in (the multi-tenant plugin's `payload-tenant` cookie) through `filterAvailableLocales`; `LanguageMarker` hides the picker unless the person can write in more than one language. (7) The dev server marks every page `noindex, nofollow` through the SEO module, so an end-to-end check for this plugin's own `noindex, follow` has to match that exact tag. (8) `fetch()` in a script cannot set the `Host` header the proxy uses to pick the site; the end-to-end check uses `node:http`. The check is `tests/e2e/multilang.e2e.mjs` (routing, fallback, `hreflang`, switcher, `noindex`, sitemap, news, required fields).
64. **Plugins own their own tables; the core's schema is the same with or without any plugin.** The rule and the author's guide are in `plugins/README.md` ("The isolation rule", "Per-site settings", "Database changes"). How it works, and what bit us: (1) **Per-site settings** are a collection in the plugin declared with `custom.polysite.siteSettings = { key, publicFields }` (`plugins/siteSettings.ts`); the multi-tenant plugin runs it in `isGlobal` mode (one row per site, the admin opens the current site's row), a Sites `afterRead` hook attaches the public fields as `site.extensions.<key>` (a missing row means no key: the plugin uses defaults; the read is wrapped so a broken row cannot take the site down), and the row's `afterChange`/`afterDelete` refresh the public site's cache. Manifest `"kind": "site-settings"` (or an array with `content-type`) makes the plugin apply BEFORE the multi-tenant plugin, content-type plugins first so the others see their collections. (2) **Migrations.** The core's `apps/cms/src/migrations` is one core-only baseline. Each plugin has `migrations/*.js` (plain ESM, `up({ db, sql })`), loaded by `plugins/pluginMigrations.ts` and passed to the adapter's `prodMigrations` after the core's, recorded as `<slug>__<file>`; Payload runs `prodMigrations` when the production server connects, and `payload migrate` (the image's CMD) still reads only the core folder. Dev still schema-pushes. (3) **`scripts/pluginMigrations.sh`** generates a plugin's migration as the difference between "the core" and "the core plus this one plugin" (`POLYSITE_PLUGINS_ONLY`, with a scratch `POLYSITE_MIGRATION_DIR`; `migrate:create` refuses a partial plugin set outside a scratch run), so it is independent of the other plugins. `check` (in `npm run check:plugin-isolation` and in `tests/e2e/run-with-plugins.sh`) fails when the core or a plugin changed without a migration, when a plugin migration alters a table or type it did not create, drops anything in `up`, or when a plugin's own tables differ depending on which other plugins are installed (`comparePluginSnapshots.mjs`). The only core objects a plugin may touch are Payload's per-collection bookkeeping columns (`payload_locked_documents_rels`, `payload_preferences_rels`, `site_urls_rels`) and the job queue's task-slug enums. A plugin's snapshot embeds the core's, so after any core migration run `rebase <slug>` for each plugin that passed `check` before. (4) **A `select` is a Postgres enum, so it must not list things that depend on what is installed.** Four fields did: `sites.enabledModules`, `roles.modules`, `site-urls.docType` (core), and the search plugin's searchable types and the notifications plugin's watched collection (the latter broke the whole seed: a query casting an unlisted collection name to the enum aborted the transaction). They are plain text now, with `components/ModuleSelect`, `SingleSelect` and `ThemeSelect` supplying the menu. (5) **A field `defaultValue` becomes a SQL default**, so `sites.theme`'s default (the first installed theme) made the core's table differ between a machine with themes and CI without; it is filled in by a hook instead. (6) `migrate:create --force-accept-warning` also disables `--skip-empty` (a blank migration gets written), so the check does not pass it. (7) Per-user state (two-factor secret, SSO links, API keys) lives in the auth plugin's own collections; API keys are a custom auth strategy, and Payload reads any `Bearer` header as a JWT, so a `me` hook is needed for `/api/users/me`. (8) A settings collection needs a stored `title` field for `useAsTitle` (a virtual field is rejected and breaks the import-map build). (9) `tests/e2e/run-with-plugins.sh` takes `E2E_PLUGINS=a,b` and `E2E_PROJECT=name` so several runs can happen side by side; its checks skip plugins that are not installed. (10) The sitemap page is cached by the web app for ten minutes, so an end-to-end check that follows other checks reads the list it is built from (`/api/__sitemap__/urls`).
65. **The webhooks plugin: signed messages to other systems, and what makes them safe to send.** Plugin notes and recipes in `plugins/webhooks/README.md`. Things that are not obvious: (1) **Events describe the live site.** Saving a draft or an autosave sends nothing, publishing sends `published` and not `updated` as well, and the message is built field by field from a fixed list (ids, titles, links; for a form submission only the form id and the submission id, never an answer), never copied from the document, with a unit test pinning that down, so a field added to a collection later cannot leak into a webhook by accident. (2) **Delivery is a Payload job per message** with exponential-backoff retries (six attempts by default, 30 seconds doubling), an event id that stays the same on every retry and replay (a receiver de-duplicates on it) and a new timestamp per attempt, signed as HMAC-SHA256 over `<timestamp>.<raw body>` so the timestamp cannot be changed; a `4xx` other than 408/429, a redirect or a refused address is not retried because it would answer the same way. After ten failures in a row the endpoint switches itself off and the admin shows a notice, so a dead receiver does not pile up work. (3) **The destination is an administrator-supplied URL the server fetches, so it is an SSRF surface.** Saving checks the scheme (https only in production), refuses credentials in the URL and names that resolve inside the network; sending checks every address the name resolves to inside the connection's own DNS lookup (a name cannot change its answer between the check and the connection), refuses loopback, private, link-local, reserved and embedded-IPv6 ranges, never follows a redirect and never reads the reply. The URL and the signing secret are AES-256-GCM encrypted (same scheme as the email and notifications plugins), masked on every read, re-read for each attempt so they never sit in the job queue, and only a Super Admin can touch webhooks or deliveries. (4) **Own tables only** (`webhook_endpoints`, `webhook_endpoints_events`, `webhook_deliveries`): the only core objects its migration touches are the per-collection bookkeeping column and the job queue's task-slug enum, the exceptions in Known Issue #64. (5) Code that writes many documents (an importer) passes `context: { skipWebhooks: true }`. (6) Third-party receivers are not equal: Zapier's Catch Hook cannot read headers and so cannot verify the signature (its URL is the credential), Slack's incoming-webhook URL rejects the payload (use the notifications plugin for people), and GitHub needs a bearer-token call Polysite does not make, hence the small relay in `examples/`. Verified by unit tests (signing and replay, address filtering, the no-personal-data rule, retry and switch-off decisions, the hooks against a stand-in for Payload, the relay), the three signature snippets run in Node, Python and PHP against a fixed vector, and an end-to-end script (`test/e2e/webhooks.e2e.mjs`). Not verified: the third-party products named in the recipes were not called, and the end-to-end script is not yet part of `tests/e2e/run-with-plugins.sh`. Not built: custom headers, payload templates, events for other collections, and email on automatic switch-off.
66. **The WordPress import plugin: a safe, repeatable import of an export file into one site.** Plugin notes in `plugins/wordpress-import/README.md`. Things that are not obvious: (1) **The input is untrusted text.** The WXR file is read by a streaming SAX parser (no whole-file DOM, so a 512 MB export is fine), and the body HTML is turned into Lexical nodes by an allow-list sanitiser (`src/html.js`): only the listed tags produce anything; scripts, styles, forms, object/embed/svg and event handlers are dropped, `javascript:` and `data:` links are rewritten away, an iframe or player becomes a link, a table becomes one line per row, and shortcodes and page-builder layouts are removed and counted. Nothing is dropped silently: the dry run counts what will be left out and the log lists it. (2) **Image download is the SSRF surface.** The host comes from the export, other hosts must be listed per import, and every connection's address is checked at connect time (private, loopback, link-local and cloud-metadata ranges refused even if a name resolves to one); redirects are followed by hand, at most three, each hop checked; the type is decided by the file's first bytes (JPEG, PNG, GIF, WebP, AVIF, PDF), never by the server's word, and SVG is refused; a size limit applies while downloading. (3) **Re-running updates instead of duplicating.** The plugin keeps its own map of which WordPress item became which document (per site and source address), so a second run updates in place, downloads no image twice and adds no redirect twice. A page or post edited in Polysite since the last import (a saved draft counts) is left alone and listed unless *Overwrite* is ticked, and an item deleted in Polysite is not brought back. Old addresses become 301 redirects only where the new address differs, never over a page that exists and never over a redirect someone else made. (4) **Cautious defaults:** everything arrives as a draft; WordPress drafts, pending, scheduled, private and trashed items are skipped unless ticked; password-protected items are never imported because they would become public. (5) **It runs as a background job** with progress on the import screen and can be started again if the server restarts. The upload is stored privately under the media volume, served by no route, and deleted with the import. (6) Who: Super Admins, and roles with `manageSiteSettings` for the sites they are assigned to; the plugin is `global` and its manifest says `"kind": "content-type"`. Posts need the posts plugin; without it pages still import and the log says the posts were skipped. Its tables are `wordpress_imports`, `wordpress_import_map` and `wordpress_import_log`; removing the plugin deletes nothing, and the content it created is ordinary content. Verified by unit tests (the reader, the sanitiser, paths and redirects, the downloader, the importer against an in-memory store) and an end-to-end script (`test/e2e/wordpress-import.e2e.mjs`, which needs `WORDPRESS_IMPORT_ALLOW_PRIVATE_HOSTS=1` to fetch from its local server). Not verified: a real WordPress export from a large live site, and the script is not yet part of `tests/e2e/run-with-plugins.sh`. Not imported: comments, users, custom fields, other post types, sub-menus, category hierarchy and the old site's front-page setting.
67. **Security review before beta (R-22): what was found, fixed and left open.** The full table (28 findings with evidence, the fix and its commit) is in `internal/SECURITY_REVIEW.md`; this is the shape of it. The method was reading every collection's access control, endpoint, hook and server-side fetch, then probing a throwaway stack (core plus eight plugins, demo data) as anonymous, Site User, Site Admin and Super Admin over REST, GraphQL and Caddy, plus `npm audit` per package. "Fixed" means committed with a test, and the regression check is `tests/e2e/security.e2e.mjs`, run by the smoke test and the plugin end-to-end run. **Found, 2 high:** page clone read the source page with the server's access, so a Site Admin could copy another site's unpublished draft into their own site (now read as the caller); and `next` and `sharp` were inside the ranges of advisories (an RCE in `next/og`, an SSRF in image optimisation; now `next` 16.3.8 and `sharp` 0.35.5, neither reachable as far as seen). **Medium, fixed:** the URL index listed drafts to anonymous visitors and any signed-in editor could edit its rows; `readVersions` defaulted to any signed-in user; the session cookie was not `Secure`; the CMS sent no security headers; placeholder secrets from `.env.example` were accepted on a public server; uploads and chunked request bodies were unbounded; Postgres was published on all interfaces with a placeholder password; a deleted document's title reached subscribers of another site (notifications); nodemailer had 13 advisories; the CMS image was on Node 20, past end of life (the images are on Node 24 LTS now); backup archives were world-readable. **Low, fixed:** any signed-in user could unlock any account; internal review notes were public; the notifications SSRF filter missed reserved ranges; sign-in had no per-address limit. **Closed since the review:** the first-run takeover (`POLYSITE_SETUP_TOKEN` is now required over https, `setup/policy.ts`) and the per-address sign-in and password-reset limits (`auth/ipThrottle.ts`, `POLYSITE_LOGIN_RATE_LIMIT`, `POLYSITE_RESET_RATE_LIMIT`), the limits live in the app because Caddy's stock image has no rate limiting. **Accepted by design:** a role with `manageSiteSettings` can run script on every visitor of its site (custom JavaScript, a custom tracking tool, unvalidated link addresses), the form limiter trusts the first `X-Forwarded-For` entry and so depends on Caddy overwriting it and on port 3001 staying unpublished, and API keys and single sign-on skip the second factor. **Still open:** backup encryption is not mandatory for an off-site copy; SMTP uses opportunistic STARTTLS; `docker-compose.prod.yml` lacks the `no-new-privileges` and `cap_drop` that the local file has; the CI/CD items (a `permissions:` block, the deploy ref passed through the environment and validated, third-party actions pinned to commit SHAs) were being rewritten by the release work at the time and are not re-checked here; whether raw script should be its own permission is a product decision. **Not reviewed:** the webhooks and WordPress import plugins, the CLI, and the release and deploy tooling, which were added during the review, and anything that needs a browser or a real certificate (Live Preview with the new admin headers, HSTS and Let's Encrypt, a CDN in front, the Cloud SQL proxy path, the off-site backup path). Traps worth keeping: a custom endpoint that passes `overrideAccess: true` skips the multi-tenant scoping as well, so read as the caller; filtering a query on a field the reader cannot read is refused by Payload (checked, so there is no blind oracle on secrets); Caddy's `request_body` limit is what bounds a chunked body, the app only sees a declared length; and the Caddyfile was normalised from CRLF to LF in the process, which makes its diff look larger than the change.
68. **Visitor search finds words in the body text, not only titles and addresses (a launch blocker for the beta).** Guide `docs/guide/search.md`, plugin notes in `plugins/search/README.md` ("How it matches"). Things that are not obvious: (1) **The text lives in the core's index, filled by the core.** `site-urls` has a `searchText` textarea, `localized: true` (so it is a column of `site_urls_locales`, one value per language like the title) and `hidden: true` (never listed in the admin or returned by the API unless a Local API caller passes `showHiddenFields`; it can still be queried). `beforeSync` fills it through `search/searchText.ts`, which calls `search/extractText.ts`: a generic walk over the collection's own field list (text, textarea, rich text; into blocks, arrays, groups, tabs and rows; Lexical flattened to words with one space between blocks, links keep their text, uploads and relationships are dropped, a block placed inside rich text contributes its prose-looking values). Never in: the title and slug (indexed separately), fields named like addresses or identifiers (`NOT_PROSE`, shared with `i18n/localize.ts`), `hidden` or `virtual` fields, **any field with its own `access.read`** (the review note), relations, uploads, selects, numbers, code and JSON. A collection opts out with `custom.polysite.searchText = false` or leaves fields out with `{ exclude: [...] }`; a content-type plugin's rich text and blocks need no code. Capped at 50,000 characters (`MAX_SEARCH_TEXT`, cut at a word); whitespace collapsed, control characters removed. (2) **Only what is live, only when published.** `beforeSync` already follows the live version of a document with drafts; the text is stored only when that version's status is `published`, so a never-published page, a draft over a live page, an unpublished page and a redirect have `""` and unpublished words never reach the index (the public API shows published entries only anyway; the plugin re-checks site and status when it reads bodies). (3) **A latent bug fixed on the way:** the live re-read in `beforeSync` passed no `locale`, so it used the request's language; during a Reindex (every language of a document in turn on one request) every language row got the request language's title. Payload does not tell `beforeSync` the language being synced, so `skipSync`, which is called with it just before, remembers it on `req.context.searchSyncLocale`, and the live read now passes it. (4) **Schema change on top of the baseline.** The pilot may already run the previous baseline, so this is a new additive core migration (`20261011_154509_search_text`: one `ALTER TABLE site_urls_locales ADD COLUMN search_text varchar`), not a regenerated baseline; `npm run check:migrations` passes (nothing destructive) and every plugin snapshot was rebased (`rebase <slug>` for all ten, then `check` green for the core and each plugin). `pluginMigrations.sh core` used to overwrite `migrations/index.ts` with a file listing only the new migration (the scratch run knows only that one); it now rebuilds the list from the folder. (5) **Existing rows get their text without manual work.** At start `backfillSearchText` (background, never blocks boot or fails it) looks per language for index rows that have a title but no `searchText`, reads the live document, and writes the text (or `""`); every row gets a string, so each is looked at once. The admin's Reindex does the same for everything (verified in the end-to-end check, including that French rows keep their French titles). (6) **Matching and cost: plain `ILIKE`, no index, measured.** Each word is one bound `like` (Postgres `ILIKE '%word%'`; Payload splits on spaces, the plugin sends one word at a time and strips `% _ \`) on title OR address OR `searchText`, ANDed over the words; no tsquery or SQL is built from what is typed. A scratch Postgres 16 with 6,000 entries of about 7 KB (2,000 for the searched site): about 90 ms for one word, linear in the site's total text (through the real endpoint, 4,000 entries of about 3 KB answered in about 110 ms). A trigram GIN index brings a body-only predicate to 2 ms but costs as much disk as the text (50 MB for 48 MB) and does not help the real query, whose OR spans `site_urls.path` and `site_urls_locales`, so the planner cannot use it (70 ms with it); a `tsvector` index would need raw SQL from the plugin and would not segment Chinese or Japanese. So: no index, the rate limits bound the load, no stemming or accent folding, the same behaviour in every script. Revisit with a generated tsvector column if a site passes tens of thousands of long pages. (7) **Ranking and snippets are the plugin's** (`query.js`): exact title 1000, title starts with the search 800, every word starts a title word 600, every word in the title 400; otherwise per word 40 or 30 in the title, 15 in the address, 4 only in the body (so more words in better places rank higher), then index priority, then title. The snippet is the item's own summary when it shows a searched word, else the 220-character window of the body with the most different words, cut at word edges; the bodies of the results on the shown page are read in one extra query. The plugin detects the column (`flattenedFields`) and on a core without it searches titles and addresses as before. The results page already marked and escaped words in titles and now does the same for snippets (text nodes, never HTML). (8) Tests: `extractText.test.ts` and `searchText.test.ts` (core), the plugin's `search.test.js` (query building, ranking, snippets, operators, feature detection) and `test/e2e/search.e2e.mjs` (a word only in a body, draft body, unpublished body, edited-in-draft body, other site's body, post bodies, escaped snippet, operators, a body past the cap, a French body, Reindex).
69. **Release and deploy design, and the backup, pinning and image-scan rules around it (SEC-10, SEC-14, SEC-16).** Guides `docs/guide/releasing.md`, `deploying.md`, `backups.md`. Things that are not obvious: (1) **A tag releases; it never deploys.** Pushing `vX.Y.Z` runs `release.yml`: `prepare` (`check-version.sh`: tag = `VERSION` = both `package.json` and lock files = a dated, non-empty `CHANGELOG.md` section, and the tagged commit is on `main` or `release/*`), then `gates` (it *calls* `ci.yml` as a reusable workflow, so a release runs exactly what every push runs), then per image (cms, web, backup) build amd64 into the local daemon, **Trivy HIGH/CRITICAL before anything is pushed**, build and push amd64+arm64 as `vX.Y.Z` only (SBOM, provenance, attestation by digest), then `smoke-published` pulls the three images *by digest* and runs the fresh-install smoke against them (`.github/scripts/smoke-images.sh`), then `promote` moves `vX.Y` and `latest` (stable releases only; `imagetools create` by digest so attestations stay attached), then a **draft** GitHub release (changelog section, the deployment bundle, `IMAGES.txt` with every digest, SBOMs, `SHA256SUMS`). A manual run of the workflow is a dry run that pushes nothing. If the published-digest smoke fails the images stay under their exact tag only and nothing moves: fix forward with the next patch, never delete the tag. (2) **Deploy is a separate manual act.** `deploy.yml` is `workflow_dispatch` only, behind the `production` environment, validates the version input against a version pattern and hands it over through `env:` (never interpolated into the remote script), SSHes to the VM and runs `deploy/deploy.sh <version>` (or `--rollback`). The script refuses a tag whose image label disagrees, takes a backup with the running backup service and test-restores it (`verify.sh`), runs the migration guard and `npx payload migrate` in a one-off container of the *new* image before any service changes, then switches cms, web and backup one at a time behind health gates (and `/api/health` must report the new version), rolling back by itself on failure (exit 3; 2 if the rollback failed too; 1 = refused before any change). State is in `.deploy/` (`audit.log`, `current.env`, `previous.env`), and **every later compose command must carry `--env-file .env --env-file .deploy/current.env`** so it uses the same digests; `POLYSITE_VERSION` and `POLYSITE_*_IMAGE` exported in the shell are ignored. (3) **Migrations are additive only; that is why rollback is images only.** The guard (`check:migrations` plus a scan of plugin `.js` migrations) refuses DROP, DELETE or TRUNCATE unless the file says `polysite:allow-destructive` and the operator passes `--allow-destructive`; older code ignores columns it does not know, so `--rollback` (and the automatic one) puts back images and the database keeps every migration. Undoing a migration itself means restoring the pre-deploy backup named in the audit log, which loses later edits. A pre-release/hotfix flow and the plugin-compatibility range (`requires.polysite`) are in the releasing guide. (4) **SEC-10: an off-site copy is encrypted or it does not happen.** `lib.sh` `offsite_block_reason` (same rules as `polysite doctor`: 16+ characters, not a placeholder, at least 10 distinct characters) is checked by `backup.sh` after the local archive is written: with `BACKUP_RCLONE_REMOTE` set and no acceptable `BACKUP_ENCRYPTION_PASSPHRASE` the local archive is kept (owner-only, `umask 077`; `restore.sh`'s safety dump too), nothing is sent (not even the checksum), the run **exits non-zero** with `Off-site copy REFUSED`, the monitoring ping gets `/fail`, `OFFSITE_STATUS` says `refused`, `healthcheck.sh` reports the container unhealthy, `entrypoint.sh` logs it at start and `verify.sh` fails with the reason. Defence in depth: only a `*.enc` name is ever passed to rclone. Consequence for deploys: the pre-deploy backup fails, so `deploy.sh` stops (`--skip-backup` is the explicit way round). Tested for real by `tests/backup/run.sh` (a throwaway Postgres and the backup image in their own Docker network, local rclone path as the remote; CI job `backup-tests`): plain local archive is mode 600, refusal without/with weak/placeholder passphrases, the encrypted archive reaches the remote and is OpenSSL-salted with no plaintext, `verify`/`restore` open it with the passphrase and refuse a missing or wrong one, a tampered archive is caught. (5) **SEC-16 pinning.** Every `uses:` is `owner/repo@<full sha> # vX.Y.Z`, resolved from the release tag within the major already in use (annotated tags dereferenced through `git/tags/<sha>`); majors are left to Dependabot, one pull request each, because its `github-actions` ecosystem reads the version comment and rewrites SHA and comment together (minor and patch updates are grouped). The Trivy scanner is a container image pinned by tag and digest in `release.yml` (`TRIVY_IMAGE`), which Dependabot does not see, so it is moved by hand. `actionlint` (container `rhysd/actionlint`) is clean. (6) **SEC-14 / the release image scan.** Scanning the three images built from the tree with the release build args found 67 (cms), 9 (web) and 35 (backup) HIGH/CRITICAL findings, nearly all fixable. Fixes: `source-map-js` 1.2.2 in both lock files; the CMS lock pins `undici` 7.29.1 (Payload pins 7.29.0 exactly) and `esbuild` 0.28.2 through npm `overrides` (the older esbuild binaries from `drizzle-kit` and `@esbuild-kit` were built with Go versions whose standard library has ~30 CVEs; 0.28.2 already ran under `tsx` and `vite`, `drizzle-kit/api`, `tsx` and `payload migrate` still work); the CMS run stage does `npm install -g npm@11` (npm's own bundled `tar`, `ip-address`; staying on the 11 line, `npm@12` is a major); the web run stage deletes npm altogether (nothing there runs it); the backup image runs `apk upgrade` (musl, zlib, libuuid, libxml2) and deletes `gosu`, a Go binary of the Postgres entrypoint that this image replaces. After that web and backup scan clean and the CMS had 5 left. Three of them (`brace-expansion` 5.0.9, CVE-2026-102276 and -102278, and `undici` 6.28.0, CVE-2026-19534, bundled inside npm) have fixed patch releases that no npm release ships yet (npm 11.21 and 12.2 both bundle the vulnerable ones), so the CMS run stage overlays npm's own copies with `brace-expansion` 5.0.11 and `undici` 6.28.1 (a block in `apps/cms/Dockerfile` to delete once an npm 11 release bundles them). **2 are left, with no fixed version anywhere:** `braces` 3.0.3 (CVE-2026-93687, via sass > chokidar and fast-glob > micromatch, build tooling) and `http-cache-semantics` 4.2.0 inside npm (CVE-2026-93748; 4.3.0 exists but its diff does not touch the max-stale code). The workflow scans without `--ignore-unfixed`, so these block a release until npm ships, or `.trivyignore` says why (an owner decision, with an expiry date); re-check with a scan of the built images before every tag, since new advisories appear daily. ## Polysite Plugin System (`plugins/`)

A separate, gitignored-from-core git repo (like `themes/`) of independently versioned extensions; see
`plugins/README.md` for the contract. The core builds and runs with none of them. How it works in the core app:

- `apps/cms/src/plugins/discoverPlugins.ts` scans `/repo/plugins/*/polysite.plugin.json` at boot and loads each `src/index.js`. The import goes through `new Function("s","return import(s)")` because Turbopack rejects a dynamic import with a non-literal path. A plugin's `package.json` **must** have `"type":"module"` or discovery skips it (the error names this). `POLYSITE_PLUGINS_OFF` (comma-separated folder names) skips plugins without deleting anything (Known Issue #55).
- `payload.config.ts` awaits discovery at top level. **Content-type plugins** (manifest `"kind": "content-type"`) are applied first, so the core's wiring (multi-tenant scoping, SEO fields, the URL index, Live Preview, the role and site module lists) can read what each of their collections declares about itself in `custom.polysite` (`apps/cms/src/plugins/contentTypes.ts`). All other plugins are applied last, so they see every collection others generated. A plugin receives a `kit` of the few core helpers it may use (access checks, slug normalisation, per-site uniqueness) instead of importing from the app. See Known Issue #54.
- A Payload plugin is a boot-time config transform, so "per-site enablement" can only be a runtime data check (`Sites.enabledModules`), never a per-request toggle. A `global` plugin is active everywhere; a `per-site` one is installed once and each site stores its own setting.
- Plugin-hosted admin components are referenced by relative path from `apps/cms/src`. That needs `turbopack.root` = repo root and a `resolveAlias` for `@payloadcms/ui` in `next.config.mjs`, and `apps/cms/.next` must be cleared after changing either. The import map is **generated** (dev container start, production build step) and gitignored; only an `importMap.d.ts` stub is committed. A plugin can also give its collection a sidebar icon in `custom.polysite.icon`.
- A plugin's web part, `plugins/<name>/web`, is a Nuxt layer discovered by `apps/web/nuxt.config.ts` the same way themes are. Its public routes register with the core's catch-all page through the content-route registry (`apps/web/utils/contentRoutes.ts`); a route that returns nothing falls through to the normal page lookup and redirects.
- `serverURL` is derived from `CMS_DOMAIN`/`CMS_SCHEME`; without it Payload builds relative password-reset links. Consequence in dev: use the admin through `http://polysite.localhost`, not `localhost:3001`.
- Secrets stored by plugins are AES-256-GCM encrypted with a key HKDF-derived from `PAYLOAD_SECRET` (one label per plugin, helper copied into each plugin so they stay independently distributable), masked on read, mask-means-keep on save.
- **Removing a plugin keeps its data**: tables and content stay in the database, a site's or role's tick on the plugin's module is kept rather than rejected, `migrate:create` refuses while a plugin is switched off, and `npm run check:migrations` fails any migration that drops data unless it says so on purpose (Known Issue #55).
- The core offers a plugin's web layer two generic hooks (`apps/web/utils/siteExtensions.ts`): named **slots** a plugin fills with components (`app` renders once for the whole app; `footer-links` renders where a layout places `<TrackingSettingsLink />`, a core component that shows whatever is in that slot) and **site events** (`form_submit`, `page_view`) a plugin can listen for. The analytics plugin's consent notice, tag loaders and cookie-settings link use them from the plugin's own `web/` layer; the core has no analytics code (Known Issue #57).
- The admin sidebar (`apps/cms/src/components/AdminNav/`) has collapsible groups and one level of sub-groups, which Payload itself doesn't have. Groups are Payload's `admin.group`; a collection or global nests under a sub-group by setting `admin.custom.navSubgroup`. Open and closed state is kept per browser in local storage (`polysite-admin-nav-open`); untouched, the first group and whichever group or sub-group holds the current page start open and the rest closed.
- A plugin that keeps per-site settings declares a collection with `custom.polysite.siteSettings = { key, publicFields }` (manifest `"kind": "site-settings"`); the core makes it one row per site and exposes the public fields as `site.extensions.<key>`, so no plugin adds a field to Sites or Users and each plugin owns its tables and migrations (`apps/cms/src/plugins/siteSettings.ts`, `pluginMigrations.ts`, Known Issue #64). A manifest may also say `"requires": { "polysite": ">=0.1.0" }`; a plugin that does not fit the running `POLYSITE_VERSION` is left out with a log line and keeps its data (`plugins/requires.ts`, `docs/guide/releasing.md`).
- Payload's own job scheduler only starts once an admin page has rendered, so the core runs due jobs itself every 30 seconds (`jobs/runner.ts`, Known Issue #61); the webhooks and WordPress import plugins rely on the same job queue.
- The plugins in the repository today: `email`, `analytics`, `posts`, `notifications`, `auth`, `i18n`, `search`, `share`, `webhooks`, `wordpress-import` (`docs/guide/plugins.md` lists what each does).

## Modules & Plugins

Started as a recommendation list; the "Add now" and "Worth adding" tiers below are now installed and verified (blocks/Media/SEO end-to-end, all 5 block types, homepage and a generic CMS page both rendering server-side — see Known Issues #10-13 for what broke along the way and how). Situational/Skip/Deferred tiers are still just that — decisions, not omissions. Package names and versions checked against the npm registry, not guessed.

### Nuxt (`apps/web`)

**Installed — tied to the product requirements:**

- **`@nuxt/image`** — official image module (responsive sizing, lazy loading, format conversion). Maps to the product requirements' "on-upload image optimization" requirement and the <1.5s load NFR.
- **`@nuxtjs/seo`** — unified SEO module (meta tags, sitemap, robots.txt, OG/Twitter cards, schema.org). Verified: rendered `<title>`, canonical link, and schema.org JSON-LD present on both the homepage and `/about-us`.
- **`nuxt-security`** — secure HTTP headers (CSP, HSTS), rate limiting, CSRF protection. `frame-ancestors` explicitly allows the CMS origin for Live Preview's iframe.
- **`@vee-validate/nuxt`** — form validation, pairing with the product requirements' "server-side validation that filters malformed email addresses" requirement for petitions.
- **`@nuxt/ui`**, **`@nuxt/icon`** — required upgrading `nuxt` itself to 4.5.2 first (see Known Issue #11); both were silently disabled under Nuxt 3 the entire time they were "installed." `@nuxt/ui` went unused beyond that fix until Known Issue #28, when its bundled Tailwind CSS v4 dependency became this project's actual styling engine (see Theme Layer's "Styling" note) — `@nuxt/ui`'s own components still aren't used, only the Tailwind pipeline it brings in.

**Installed — low-risk, broadly useful:**

- **`@vueuse/nuxt`** — standard Vue composition-utilities collection.
- **`@nuxt/fonts`** — self-hosts/optimizes web fonts, reduces render-blocking and layout shift.

**Situational — confirm the need first:**

- **`@nuxtjs/i18n`** — only if a site needs more than one language. Restructures routing/content if adopted later, so decide before building more pages, not after.
- **`@pinia/nuxt`** — only once client-side state gets genuinely complex (multi-step forms, etc.).

**Skip:**

- **`@nuxt/content`** — for markdown-file-driven content, which conflicts with the Payload-CMS-driven model already built.

### Payload CMS (`apps/cms`)

**Installed — tied to the product requirements:**

- **`@payloadcms/plugin-form-builder`** — official dynamic form builder plugin (fields + a submissions collection). The product requirements ask for exactly this for petitions — likely covers most of that requirement rather than needing to be hand-built.
- **`@payloadcms/plugin-seo`** — official SEO plugin: meta title/description/image fields on any collection. Pairs with `@nuxtjs/seo` on the frontend — CMS holds the values, Nuxt renders them. Adding it registered a new admin preview component that needed `payload generate:importmap` re-run (Known Issue #13).
- **`sharp`** — image-processing dependency for the `Media` uploads collection (built — local-disk storage, thumbnail/card sizes, WebP conversion), needed for the same "on-upload image optimization" NFR as `@nuxt/image` above. Must be explicitly imported and passed as a top-level `sharp` key in `buildConfig`, not just installed (Known Issue in the numbered list above).

**Worth adding when the matching feature gets built:**

- **`@payloadcms/plugin-redirects`** — not used: redirects are the core's own `redirects` collection, which adds per-site scoping and form/media targets.
- **`@payloadcms/plugin-nested-docs`** — hierarchical pages (parent/child, breadcrumbs), if nested informational pages become a real need.
- **`@payloadcms/plugin-search`** — installed; it builds the `site-urls` index of every address a site answers to. Visitor-facing search is the optional `search` plugin (`plugins/search`), which reads this index and then re-reads each hit live as an anonymous visitor.

**Skip — contradicts a decision already made:**

- **`@payloadcms/plugin-cloud-storage`** / **`@payloadcms/storage-gcs`** — would push media uploads to Cloud Storage, but the product requirements already decided uploads stay on the VM's own disk specifically to avoid that managed-service cost. Only reconsider if that cost decision changes.

**Installed — pulled forward from Deferred, per an explicit user decision (Known Issue #29):**

- **`@payloadcms/plugin-multi-tenant`** — was originally deferred until after the first deployment; it was pulled forward deliberately. Replaces the hand-rolled `userSiteIds`-based site-scoping in `Pages.ts`/`Media.ts` with Payload's official pattern. See Known Issue #29 for the migration and the two more Known Issue #10 prompts it produced.
